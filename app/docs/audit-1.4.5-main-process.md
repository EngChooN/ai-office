## 항목별 상세

### 1. 2초마다 전체 현황(스냅샷)을 통째로 다시 보냄 — 위험도 중간 · 추천: 고침
- **무엇**: `external.ts`의 `poll()`이 2초마다 돈다. 끝에서 `hooks.sync()`를 부르고, 이게 `office.ts`의 `scheduleEmit()`을 **내용이 바뀌었는지 보지 않고 항상** 부른다(`office.ts:462-466`). 그러면 50ms 뒤 `snapshot()`이 만들어져 화면 창·비서 창(IPC), 트레이, 휴대폰으로 전부 전달된다(`index.ts:321-330`).
- **왜 낭비인가**: 스냅샷은 매번 DB 질의(`usageByStaffBetween`, `office.ts:652`)를 하고, 업무 카드 655건 전체(결과글 합 약 1.25MB, 측정)와 직원·팀·회의 등을 담는다. 대표가 아무것도 안 해도, 창이 숨겨져 있어도 하루 종일 돈다.
- **추정 규모**: 스냅샷 1개 약 1.5MB 안팎(추정) × 하루 43,200번. 실제 크기는 측정 못 함.
- **고치는 방향**: 외부 세션 목록이 이전과 같으면 `sync`를 부르지 않는다(비교 후 변했을 때만). 동작·화면은 그대로.
- **전/후 측정**: 앱을 켠 채 5분 두고 ① `scheduleEmit` 호출 횟수(임시 카운터) ② 메인 프로세스 CPU(`top -pid`) ③ `JSON.stringify(snapshot()).length`. 기대: 호출 150회 → 0~수 회.

### 2. 첨부 파일 하나 찾을 때마다 폴더 전체를 읽음 — 위험도 중간 · 추천: 고침
- **무엇**: `attachments.ts:50-54` `findById`가 `readdirSync`로 첨부 폴더 전체(현재 862개, 521MB)를 읽고 앞부분이 맞는 파일을 찾는다. 이미지 한 장을 화면에 띄울 때(`protocol.handle`)마다, 휴대폰이 첨부를 요청할 때마다 실행된다. 동기 호출이라 그동안 메인 프로세스가 멈춘다.
- **고치는 방향**: 첫 호출 때 `id → 파일명` 표를 한 번 만들고 저장·삭제 때만 갱신. 또는 파일명을 id로 직접 접근.
- **전/후 측정**: 대화에 이미지 30장이 있는 방을 열 때 `findById` 총 시간 합(임시 타이머). 파일 수 862개 기준 호출 1번당 수 ms × 30회 → 거의 0.

### 3. 기록 한 줄 저장마다 디스크 완전 동기화 — 위험도 낮음 · 추천: 고침
- **무엇**: `db.ts` `openDb()`에 `PRAGMA`가 없다. 현재 설정은 `journal_mode=delete`, `synchronous=FULL`(측정). 그래서 `insertLog` 한 줄마다 디스크에 완전히 쓰고 기다린다. 직원이 일하는 동안 로그가 계속 들어온다.
- **측정**: 실제 DB 복사본에 300줄 넣기 — 현재 설정 264ms, WAL+NORMAL 44ms (줄당 0.88ms → 0.15ms, 약 6배).
- **주의**: WAL은 `office.db-wal`·`-shm` 파일이 생겨 백업·이동(`userDataMigrate`, `.bak` 만들기)이 이 파일들을 함께 다루는지 확인해야 한다. 그래서 위험도를 "낮음"으로 두되 작업 전 확인 필요. 대안: WAL 없이 여러 줄을 묶어서(트랜잭션) 저장.
- **효과 크기**: 줄당 1ms 미만이라 눈에 띄는 체감은 작다. 4번과 함께 하거나 "눈에 띄는 효과 없으면 건드리지 않는다" 원칙상 보류도 가능.

### 4. 로그·사용량·대화·첨부가 영원히 쌓임 — 위험도 중간 · 추천: 정책을 정한 뒤 고침
- **측정(현재 DB 53MB)**: 로그 71,178줄(글자 13.2MB), 대화 7,997건(2.9MB), 사용량 3,514건, 결재 기록 2,923건, 첨부 862개 521MB, 산출물 106MB. 정리되는 표는 결재 기록(90일)과 비서 대화뿐이다. 로그·대화·사용량·첨부는 직원을 지울 때만 지워진다(`db.ts:643-646`, 첨부는 `attachments.ts:80`의 직접 삭제뿐).
- **영향**: 지금은 문제없는 수준이나 계속 늘어난다. 로그 검색(`LIKE '%…%'`, `db.ts:755`)은 전체를 훑는다. 데이터 폴더 1.4GB 중 첨부가 가장 크다.
- **고치는 방향**: 오래된 첨부(예: 어떤 대화·카드에도 안 쓰이는 것), 오래된 로그를 정리. **동작이 달라지는 변경(대표가 예전 기록을 못 보게 됨)이라 보존 기간은 대표가 정해야 한다.**
- **전/후 측정**: DB 크기, 시작 시간(`openDb`~창 표시), 첨부 폴더 용량.

### 5. 종료 때 정리 빠짐 — 위험도 낮음 · 추천: 고침
- `before-quit`(`index.ts:431`)에서 `db.close()`가 불리지 않는다(`closeDb`는 테스트용으로만 쓰임). 지금 저장 방식에서는 문제가 드물지만, 3번(WAL)을 하면 닫기가 필요하다.
- `office.stop()`(`office.ts:638-645`)이 대기 중인 `emitTimer`(50ms)를 정리하지 않아, 종료 순간 이미 멈춘 모듈에 마지막 스냅샷을 보낼 수 있다.
- 외부 훅 서버(`external.ts:105-110`)는 413 응답 뒤 `req.destroy()`만 하고 `end` 처리 경로가 남는다 — 실제 오류는 확인 못 함(추정).
- 타이머 정리 상태(확인함): `setInterval`은 모두 `stop`/`closeAll`에서 해제되고 `unref`도 대부분 걸려 있다. 파일 감시자(`fs.watch`)는 없다. 닫히지 않는 감시자·연결은 못 찾았다.

### 6. 2초 폴링이 등록 파일을 매번 전부 읽음 — 위험도 낮음 · 추천: 보류
- `readRegistry()`가 `readdirSync` + 파일마다 `readFileSync`+`JSON.parse`, 그리고 `process.kill(pid, 0)`(`external.ts:310-336`). 파일 수가 적어(터미널 세션 수) 비용이 작다. 1번을 고치면 영향이 더 줄어든다. 측정에서 눈에 띄는 비용이 안 나오면 건드리지 않는다.
- 코덱스 세션 폴더 스캔은 6초마다(`external.ts:22,281`) — 이미 간격을 두고 있어 보류.

### 7. `office.ts` 5075줄 — 위험도 낮음 · 추천: 이번엔 보류
- 구조상 가장 큰 덩어리(다음은 `db.ts` 1211, `secretary.ts` 917). 쪼개면 회귀 위험이 크고 속도 효과가 없다. 별도 단계에서 `snapshot()` 조립·타이머 묶음부터 떼는 것을 제안한다.

## 휴대폰 연결 통신량 (확인한 것)
- 이미 줄여 둔 것: 스냅샷·상태는 500ms에 한 번 마지막 값만 묶어 보냄(`remote/events.ts:171`), 보관 이벤트 최대 500개·시간 제한, 하트비트 15초, 느린 연결 감지. 이 부분은 건드리지 않는 것을 추천.
- 남은 문제: 1번 때문에 2초마다 "새 스냅샷"이 생기면 휴대폰에도 계속 전달된다(`remote.publish`). 1번만 고쳐도 같이 줄어든다. 스냅샷이 매번 통째라 변화분만 보내는 방식은 동작 방식 변경이라 범위 밖.
- 실제 휴대폰 연결 상태의 통신량(바이트/분)은 이번에 측정하지 못했다(확인 못 함).

## 이번에 확인 못 한 것
- 시작 시간·메모리 사용량의 절대값(앱을 띄워 측정하지 않음). 측정 방법: `app.whenReady` → 창 `ready-to-show` 시간 로그, `process.memoryUsage()`를 5분·1시간 간격으로 기록.
- 렌더러(화면) 쪽 긴 목록 성능은 이번 범위(메인 프로세스) 밖.
- 윈도우에서의 동작.
