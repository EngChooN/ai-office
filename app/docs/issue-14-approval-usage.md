# 이슈 #14 조사: 승인 요청 과다 · 사용량 실시간 반영 · 토큰 사용

조사만 했고 코드는 고치지 않았습니다. 앱 화면에서 재현하지는 못했고, 코드 읽기로 정리한 원인 후보입니다.

## 1. 승인 요청이 너무 많은 이유 (a)

### 승인이 흐르는 길
`hired.ts` `canUseTool` → (장비로 허용·읽기 전용 명령이면 통과) → `office.ts` `autoDecide` (2174행~) → 판정은 `shared/autoApprove.ts`.
`autoDecide`는 **자동결재 시간대가 켜져 있거나 자율 진행일 때만** 대신 판정하고, 아니면 곧바로 결재함으로 보냅니다. 판정 결과가 '기다림'이면 자동결재 모드에서는 결재함에 올리고, 자율 모드에서는 거부합니다(`autonomyVerdict`).

### 자동·자율 모드인데도 묻는(또는 거부하는) 경우
| # | 요청 | 근거 | 영향 |
|---|---|---|---|
| A | **직원이 방금 고친 파일 이름이 들어간 명령** (예: `index.ts`를 고친 뒤 `git add src/index.ts`, `grep … index.ts`) | `office.ts:2231` `autoWritten`에 경로와 **파일 이름만(basename)**도 넣고 `command.includes()`로 비교 | 가장 유력. 이름이 짧거나 흔하면(`types.ts`, `index.ts`) 무관한 명령도 걸림 |
| B | **`package.json`·`Makefile`을 고친 뒤의 모든 `npm/pnpm/yarn/npx/make` 명령** (`pnpm typecheck`, `pnpm test` 포함) | `office.ts:2233`, `autoWroteBuildFile` | 개발 업무에서 가장 흔한 흐름이 막힘 |
| C | **A·B의 기록이 지워지는 때가 '자동결재 시간대 시작' 한 번뿐** | `office.ts:2140`. 자율 진행(업무 카드·지시창 스위치)은 시간대와 무관하게 `autoWritten`에 계속 쌓이는데 비우는 곳이 없음 | 앱을 오래 켜 둘수록 걸리는 명령이 늘어남. 자율 모드에서는 '거부'라 직원이 작업을 건너뜀 |
| D | 스크립트 실행: `python x.py`, `node x.js`, `bash x.sh`, 인라인 코드(`-c`·`-e`) | `autoApprove.ts:301` `interpreterRuns` — 파일 인자만 있어도 기다림 | 의도된 안전장치. 다만 직원이 만든 테스트 스크립트 실행도 전부 걸림 |
| E | 목록에 없는 명령 (fail closed) | `autoApprove.ts:385` `isKnownCommand` | `pnpm`·`npx`는 허용이지만 `xcodebuild` 같은 도구는 걸림 |
| F | 파일 편집이지만 위험 경로 | `autoApprove.ts:~900` `DANGEROUS_WRITE`: `.claude/`, `.github/workflows/`, `.husky`, `.envrc`, 셸 rc, **내용이 `#!`로 시작하는 파일** | 쉘 스크립트·훅 편집이 걸림. 일반 소스 편집은 통과 |
| G | `git push`, 배포, 삭제(`rm -r`), `sudo`, 쓰기 MCP, 화면 캡처, 브라우저 클릭·입력, `?`/`#` 붙은 WebFetch | 의도된 대기 | 설계대로 |

### 자동·자율이 꺼져 있을 때 (기본값)
- 직원 결재 방식 `approvalMode`는 `ask`(모두 묻기)와 `acceptEdits`(파일 수정만 자동) 두 가지입니다 (`hired.ts:348`). 새 직원 기본이 `ask`이면 **파일 편집마다 승인 카드**가 뜹니다.
- 자동결재가 꺼져 있고 자율도 아니면 `autoDecide`는 `null`을 돌려주고 모든 요청이 결재함으로 갑니다. 대표가 "자동"으로 설정했다고 생각해도, **직원별 결재 방식과 자동결재 시간대는 별개 설정**이라 어긋날 수 있습니다. 설정 화면에서 어느 것이 켜졌는지 한눈에 보이는지 확인이 필요합니다.
- Codex 직원은 `acceptEdits`여도 `Edit` 도구만 자동이고 `Write`·셸은 평소 결재입니다 (`codex.ts:368`).
- "앞으로 항상 승인" 규칙(`approvalRules.ts`)은 직원·명령 머리 단위라서, `git diff`·`git status`처럼 하위 명령별로 따로 만들어야 합니다.

### 원인 후보 순위
1. **C → A·B** (고친 파일 추적 기록이 지워지지 않고 이름만으로 비교): 코드를 고칠 때마다 이후 명령이 막히는 증상과 가장 잘 맞음.
2. 직원이 `ask` 모드이거나 자동결재 시간대가 꺼져 있음 (설정 인지 문제).
3. D·F (스크립트·`#!` 파일).

## 2. 사용량이 실시간으로 반영되지 않는 이유 (b)

갱신 시점은 아래 넷뿐이고 **주기적 조회는 없습니다**.
- **Claude**: 직원이 Claude를 부르는 도중 CLI가 `rate_limit_event`를 줄 때만 (`ai/claude.ts:265` → `office.ts:3654 onRateLimit`). 일을 안 하면 값이 멈춰 있고, 그 이벤트에 어느 창(5시간·주간)이 들어오는지도 CLI 마음입니다.
- **수동 새로고침 버튼** (`PlanUsageCard.tsx:96` → `refreshPlanUsage`): haiku로 "." 한 번 호출해 값을 받음 (비용 1센트 미만이지만 토큰을 씀).
- **Codex**: 앱 시작 때 1회(`index.ts:402`)와 새로고침 버튼. 그 외 턴 중 이벤트(`office.ts:383`).
- 화면 시계: 카드는 `updatedAt`을 "~기준"으로 표시하지만 자동으로 다시 읽지 않습니다. 80·100% 알림도 값이 들어올 때만 판단합니다.

원인: Claude 사용률을 조회하는 별도 API 없이 **대화 호출의 부산물**로만 받습니다. "실시간"은 구조상 불가능하고 "최근 값"만 가능합니다.

## 3. 토큰을 많이 쓴다 (c) — 확인 범위
- 새로고침 버튼 1회 = 짧은 호출 1번(작음).
- 직원마다 시스템 프롬프트에 팀 문맥(`teamContext`), 참고 문서, 인격 글(최대 4,000자), 합쳐서 최대 8,000자를 매 세션에 붙입니다 (`hired.ts:26`).
- 승인 거부가 반복되면 직원이 같은 일을 다른 방식으로 재시도해 토큰이 늘 수 있습니다(자율 모드의 거부 → 재시도). 즉 (a)가 (c)의 원인일 가능성이 있습니다.
- 직접 토큰 실측은 하지 못했습니다. 급여·사용 기록 화면(`addTaskUsage`)으로 직원별 사용량을 먼저 보는 것을 권합니다.

## 4. 고칠 방법

### 방법 1 (추천): 고친 파일 추적을 정밀하게 (a의 주원인)
- `autoWritten` 비교를 basename 포함 일치에서 **경로 전체(절대·상대 정규화) 일치**로 바꾸고, 인터프리터·실행 명령(`./x`, `bash x`, `node x`)이 그 파일을 실행하는 경우에만 막음.
- `autoWroteBuildFile`은 `npm run <스크립트>`처럼 **스크립트 실행**일 때만 막고, `test`·`typecheck` 같은 알려진 이름은 package.json의 scripts가 바뀌지 않았다면 통과(또는 변경 후 `scripts` 값이 바뀐 경우만 막기).
- 기록을 **직원·카드 단위로 두고**, 업무 시작·완료·자율 진행 시작 때 비움(C 해소).
- 영향 범위: `office.ts` `autoDecide` 일부, `autoApprove.ts`(판정 함수 추가), 시험 `autoApprove`·`autonomy` 계열. 안전 규칙(H2: 쓴 파일을 실행해 우회)을 약하게 하므로 **보안 검토 필요**.
- 예상 작업량: 코드 0.5~1일, 시험·보안 검토 0.5일.

### 방법 2: 설정 쪽 안내와 기본값 (a의 설정 어긋남, 가벼움)
- 결재 화면과 직원 프로필에 "자동결재 꺼짐 / 이 직원은 모두 묻기"를 한눈에 보이게 하고, 새 직원 기본을 `acceptEdits`로 하는 안(대표 결정 필요).
- 막힌 이유를 결재 카드에 한 줄로 표시("방금 고친 파일을 실행하려 해서 기다려요") — 대표가 원인을 알고 "항상 승인"으로 풀 수 있게.
- 영향 범위: `hired.ts`·renderer 설정·결재 카드, i18n 4개 언어. 안전 규칙은 그대로.
- 예상 작업량: 0.5일.

### 사용량 (b)
- 자동 갱신을 넣으려면 앱이 열려 있고 화면에 카드가 보일 때 N분(예: 10분)마다 `refreshPlanUsage`를 부르는 방법이 있으나, **호출마다 토큰을 쓰므로(c)와 충돌**합니다. 대안: "마지막 갱신 N분 전" 문구와 직원이 일한 직후(턴 종료 시) 값 갱신 표시를 눈에 띄게 하는 것 — 비용 없음, 0.5일.
- 정말 실시간이 필요하면 Claude 쪽에 사용률 조회 수단이 있는지 먼저 확인해야 합니다(현재 CLI에서는 `rate_limit_event`뿐으로 확인). 이 확인은 못 했습니다.

## 5. 가정과 확인하지 못한 것
- 앱 실행 화면에서 재현하지 않았습니다. 원인 순위는 코드 읽기 기반입니다.
- 새 직원의 기본 결재 방식 값과 설정 화면 문구는 확인하지 않았습니다.
- 대표가 실제로 켠 것이 자동결재 시간대인지, 업무 카드의 자율 스위치인지, 직원별 결재 방식인지 이슈 글만으로는 알 수 없습니다. 이 구분이 방법 1·2 선택에 영향을 줍니다.
