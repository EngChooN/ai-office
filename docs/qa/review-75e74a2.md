## 꼭 고칠 것

### 필수 1) 폴더가 중첩되면 기록이 안 맞아 통과
키가 작업 폴더 문자열 정확 일치라서 상위·하위 폴더에서 일하는 직원끼리 서로의 기록을 못 본다.
- 재현 1: 직원 A(cwd `/repo`)가 `/repo/app/package.json`의 test 스크립트를 바꿈 → 직원 B(cwd `/repo/app`)의 `npm test` → **기록 없음 → 통과**(자동 승인). 반대로 A가 `/repo/app`에서 `echo x > scripts/e.test.mts`(상대 경로로 기록)를 하고 B가 `/repo`에서 `pnpm test`/`pnpm -C app test` → 통과.
- 모노레포·랩 폴더를 상위로 둔 직원과 하위로 둔 직원이 함께 일하는 흔한 구성이라 실제 위험이 있다. 이번 QA 2번과 같은 종류의 우회다.
- 고칠 방향: 조회(`get`)·기록(`rec`) 시 cwd가 같은 키뿐 아니라 **조상·자손 관계인 키**도 함께 검사. 가장 단순하게는 `get(cwd)`가 접두사 관계(`a === b || a.startsWith(b + '/') || b.startsWith(a + '/')`)인 모든 레코드를 합쳐 검사. 상대 경로로 기록된 파일은 레코드 폴더 기준이라, 합칠 때 폴더가 다른 레코드는 `files`·`scripts`를 절대 경로(키 + '/' + 상대)로 풀어 비교하거나, 중첩 관계가 있으면 보수적으로 "러너 전부 대기"로 본다. 시험: 위 두 재현.

## 권장(필수 아님)
- **심볼릭 링크·실경로:** 키는 문자열 정규화뿐이라 `/tmp/x`와 `/private/tmp/x`(macOS), 심볼릭 폴더 링크는 다른 폴더로 본다(`/private/repo` → 기록 없음 확인). 폴더 키를 만들 때 `fs.realpathSync`(실패 시 원본)를 쓰면 해소. 파일 경로가 링크를 통과하는 경우도 같음.
- **결재 과다:** 기록이 폴더에 영구 보관되므로, 테스트 파일·`scripts/` 아래 파일 하나만 고쳐도(대표가 승인한 정상 수정 포함) 그 폴더의 `pnpm test`·npm 스크립트가 앱 재시작 전까지 계속 wait. 자율 진행에서는 곧 거부라 테스트를 못 돌린다. 대표가 직접 승인한 러너 실행은 기록에서 `runnable`·`scripts`를 비우거나, 승인된 쓰기(대표가 본 쓰기)는 기록에서 제외하는 방안 검토. 보안 약화 없이 과다만 줄이는 쪽으로.
- **앱 재시작:** 기록은 메모리뿐이라 재시작하면 사라진다. 수정 → 재시작 → `npm test`는 통과. 필요하면 폴더별 요약(스크립트 해시 등)을 저장하는 방안이 있으나 범위가 커서 미뤄도 됨.
- **메모리:** 폴더 수·파일 수 모두 상한이 없다(5000개 쓰기 → `files` 5000개 유지). 500 초과는 `runnable`만 켜고 계속 추가한다. 500을 넘으면 추가 기록을 멈춰도 같은 효과(이미 러너 전부 대기)라 파일 집합 증가를 막는 편이 좋다. 규모가 작아 급하지 않음.
