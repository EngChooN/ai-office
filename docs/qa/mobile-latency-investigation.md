# 휴대폰 앱 반응 느림 조사

## PC 쪽 (강백엔 · 백엔드)

조사만 했고 코드는 고치지 않았습니다. (휴대폰 앱 쪽 절은 임안드가 이 문서 아래에 따로 씁니다.)

### 한 줄 결론
PC는 버튼을 받자마자 **5~7ms** 만에 처리해서 느린 쪽이 아닙니다. 그런데 **승인·반려·직원 상태 변화는 "상태 전체 묶음(snapshot)"이 와야 화면에 반영되고, 그 묶음이 일부러 약 0.55초 늦게 나갑니다.** 이것이 PC 쪽의 가장 큰 원인입니다. 휴대폰 화면도 누르자마자 먼저 반영하는 처리가 없어서, 이 지연이 그대로 체감됩니다.

### 재는 방법
- 실제 데이터는 건드리지 않았습니다. 임시 폴더(HOME·앱 데이터)에 실제 사무실(Office)과 실제 원격 서버(HTTPS, `/v2/call`, `/v2/events`)를 띄우고, AI 엔진만 가짜로 두었습니다.
- 직원 10명, 직원당 기록(log) 200개, 대화 300개를 넣었습니다(기록·대화를 10배로 늘려도 snapshot 크기 불변).
- 같은 PC 안(127.0.0.1)에서 쟀습니다. **실제 Wi-Fi의 왕복 시간은 빠져 있습니다**(아래 "확인 못 한 것").
- 시험 스크립트는 저장소에 넣지 않았습니다(임시 폴더에서만 실행). 필요하면 다시 만들어 드릴 수 있습니다.

### 측정값 (반복 8회 중앙값)
| 항목 | 측정값 |
|---|---|
| ① `decide`(승인·반려) → `/v2/call` 응답까지 | 5.7ms (3.8~7.0) |
| ① `sendChat`(메시지 보내기) → 응답까지 | 6.8ms (5.0~11.8) |
| ② 승인 처리 후 화면 반영용 snapshot이 나가기까지 | **551ms** (최소 36 ~ 최대 553) |
| ② 메시지 보낸 뒤 대화 말풍선 이벤트(`chat`)가 나가기까지 | 6.6ms (바로 나감, 묶음 없음) |
| ② 메시지 보낸 뒤 직원 상태 변화 snapshot이 나가기까지 | **557ms** |
| ③ snapshot 한 번 크기 (직원 10명) | 11.2KB (직원 1명 약 0.9KB) |
| ③ 같은 snapshot을 gzip으로 압축하면 | 1.9KB (약 1/6) |
| ③ PC가 snapshot을 만드는 시간 | 1.2ms~4ms |
| ⑤ 응답 압축(Content-Encoding) | **없음** |
| ⑤ 연결 재사용(keep-alive) 유지 시간 | PC 서버 5초(Node 기본값, 따로 설정 안 함) |
| ⑤ 새 HTTPS 연결 vs 재사용 (같은 PC 안) | 3.3ms vs 1.0ms |

### 원인 후보별 정리 (큰 순서)

**1. snapshot 500ms 묶음 + 50ms 갱신 대기 — 영향 큼 (체감 약 0.5~0.6초)**
- 근거: `main/remote/events.ts`의 `SSE_LIMITS.coalesceMs = 500`, `publish()`가 첫 값을 받아도 **바로 보내지 않고 타이머 500ms 뒤에** 마지막 값을 보냅니다(맨 앞 값부터 보내는 방식이 아님). 그 앞에 `office.ts`의 `scheduleEmit()` 50ms 대기가 한 번 더 있습니다. 승인 처리 → snapshot 반영이 실측 약 550ms입니다.
- 영향: 승인 카드가 사라지는 것, 직원이 "대기 → 일하는 중"으로 바뀌는 것이 모두 이만큼 늦게 보입니다. 휴대폰 데이터 속도와 상관없이 항상 생기는 지연입니다.
- 고칠 방법: 묶음을 "처음 값은 바로, 그 뒤 500ms 동안 온 것만 묶어서 한 번 더"(앞쪽 즉시 발송 + 뒤쪽 묶음)로 바꿉니다. 또는 사람이 누른 호출(decide·sendChat 등) 직후에는 묶음을 건너뛰고 즉시 보냅니다(`handleV2Call` 뒤에 `flush`). 부수 효과: 작업이 많을 때도 최대 초당 약 2회→앞쪽 즉시 + 뒤쪽 2회로 늘 뿐이라 데이터 부담은 작습니다(11KB × 연결 2개).
- 난이도: 낮음. `events.ts` 한 곳(약 10줄)과 시험 수정.

**2. 누르자마자 화면에 먼저 반영하는 처리가 없음 (휴대폰 화면 쪽, PC 쪽 근거만) — 영향 큼**
- 근거: 승인 버튼은 `window.office.decide()`만 부르고(`ApprovalTab.tsx:59`) 카드는 snapshot이 와야 사라집니다. 로컬 상태를 먼저 바꾸는 코드가 없습니다. 메시지 보내기는 입력창만 먼저 비우고 말풍선은 PC가 `chat` 이벤트를 보낸 뒤에야 나옵니다(`ChatPage.tsx` handleSend). 휴대폰은 "call 응답 → 이벤트/snapshot" 2번을 순서대로 기다리는 구조입니다.
- 영향: 원인 1의 지연 + 왕복 시간이 모두 화면에 그대로 드러납니다.
- 고칠 방법: 승인·반려는 누르는 즉시 카드를 "처리 중"으로 바꾸거나 숨기고, 실패하면 되돌립니다(앞서 만든 결재 카드의 `decideOutcome` 같은 방식). 메시지는 보낸 즉시 "보내는 중" 말풍선을 보여 주고 `chat` 이벤트로 확정합니다. **휴대폰 앱 쪽 작업이라 임안드 절과 함께 판단해 주세요.**
- 난이도: 중간(되돌리기·중복 방지 처리 필요).

**3. 연결을 5초만 재사용 + 압축 없음 + HTTP/1.1 — 영향 중간(추정, 실제 Wi-Fi 확인 필요)**
- 근거: `server.ts`가 `keepAliveTimeout`을 따로 설정하지 않아 Node 기본 5초입니다. 5초 넘게 가만히 있다가 누르면 연결이 끊겨 있어 TCP+TLS 핸드셰이크를 새로 합니다(같은 PC 안에서는 +2.3ms지만, 실제 Wi-Fi에서는 왕복 시간×2~3회로 **추정 60~300ms**). 응답 압축도 없습니다(snapshot 11.2KB → 1.9KB로 줄 수 있음).
- 영향: 승인·전송 같은 짧은 호출은 이미 작아서(응답 수십 바이트) 압축 효과는 작고, snapshot을 새로 받을 때(재연결·앱 복귀) 효과가 큽니다.
- 고칠 방법: `https.createServer` 뒤에 `server.keepAliveTimeout = 60_000`(헤더 타임아웃도 함께 조정), `/v2/call` 큰 응답(snapshot·기록)에 gzip 적용(요청 `Accept-Encoding` 확인). SSE(이벤트 스트림)는 압축하지 않습니다.
- 난이도: 낮음(keep-alive) / 낮음~중간(gzip, 응답 크기 한도·SSE 예외 처리).

**4. snapshot이 직원 한 명만 바뀌어도 전체를 다시 보냄 — 영향 작음(현재 규모)**
- 근거: 11.2KB, 직원 1명 0.9KB. 기록·대화는 snapshot에 들어 있지 않아(별도 호출) 쌓여도 커지지 않았습니다. PC가 만드는 시간도 1~4ms입니다.
- 영향: 직원 10명 정도에서는 느림의 원인이 아닙니다. 직원·업무 카드가 수십~수백 개가 되면 커질 수 있지만 이번에 쓸 만한 실측은 못 했습니다.
- 고칠 방법: 바뀐 직원만 보내는 부분 갱신(diff)은 규격 변경이 커서 지금은 권하지 않습니다. gzip(3번)이 먼저입니다.
- 난이도: 높음.

**5. PC 처리 자체 — 영향 없음**
- `/v2/call` 5~7ms, 인증·검사 코드는 sha256 비교뿐이라 가볍고(`auth.ts`), 처리 시간 한도(timeout)도 걸림돌이 아닙니다. 고칠 필요 없음.

### 확인 못 한 것
- **실제 휴대폰·Wi-Fi·Tailscale·인터넷 경로의 왕복 시간**: 같은 PC 안에서만 쟀습니다. 3번의 핸드셰이크 비용은 추정입니다. 휴대폰에서 `/v2/call` 시작~끝 시간을 찍어 보면 확정됩니다(임안드 절).
- PC가 AI 작업으로 바쁠 때(엔진 출력이 몰릴 때)의 응답 시간. 가짜 엔진이라 이 상황은 재현하지 못했습니다.
- 직원 수십 명·업무 수백 개일 때의 snapshot 크기.
- 휴대폰이 `/v2/events`를 끊고 다시 붙는 상황(앱 복귀)의 따라잡기 시간.

### 권장 순서
1. snapshot 묶음 방식 변경 (난이도 낮음, 효과 가장 큼, PC만 고치면 됨)
2. 휴대폰 화면의 즉시 반영 (임안드와 같이 결정)
3. keep-alive 60초 + gzip
