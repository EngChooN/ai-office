# 휴대폰 앱 반응 느림 조사

## PC 쪽 (강백엔 · 백엔드)

조사만 했고 코드는 고치지 않았습니다. (휴대폰 앱 쪽 절은 임안드가 이 문서 아래에 따로 씁니다.)

### 한 줄 결론
PC는 버튼을 받자마자 **5~7ms** 만에 처리해서 느린 쪽이 아닙니다. 그런데 **승인·반려·직원 상태 변화는 "상태 전체 묶음(snapshot)"이 와야 화면에 반영되고, 그 묶음이 일부러 약 0.55초 늦게 나갑니다.** 이것이 PC 쪽의 가장 큰 원인입니다. 휴대폰 화면도 누르자마자 먼저 반영하는 처리가 없어서, 이 지연이 그대로 체감됩니다.

### 재는 방법
- 실제 데이터는 건드리지 않았습니다. 임시 폴더(HOME·앱 데이터)에 실제 사무실(Office)과 실제 원격 서버(HTTPS, `/v2/call`, `/v2/events`)를 띄우고, AI 엔진만 가짜로 두었습니다.
- 직원 10명, 직원당 기록(log) 200개, 대화 300개를 넣었습니다(기록·대화를 10배로 늘려도 snapshot 크기 불변).
- 같은 PC 안(127.0.0.1)에서 쟀습니다. **실제 Wi-Fi의 왕복 시간은 빠져 있습니다**(아래 "확인 못 한 것").
- 시험 스크립트는 저장소에 넣지 않았습니다(임시 폴더에서만 실행). 필요하면 다시 만들어 드릴 수 있습니다.

### 측정값 (반복 8회 중앙값)
| 항목 | 측정값 |
|---|---|
| ① `decide`(승인·반려) → `/v2/call` 응답까지 | 5.7ms (3.8~7.0) |
| ① `sendChat`(메시지 보내기) → 응답까지 | 6.8ms (5.0~11.8) |
| ② 승인 처리 후 화면 반영용 snapshot이 나가기까지 | **551ms** (최소 36 ~ 최대 553) |
| ② 메시지 보낸 뒤 대화 말풍선 이벤트(`chat`)가 나가기까지 | 6.6ms (바로 나감, 묶음 없음) |
| ② 메시지 보낸 뒤 직원 상태 변화 snapshot이 나가기까지 | **557ms** |
| ③ snapshot 한 번 크기 (직원 10명) | 11.2KB (직원 1명 약 0.9KB) |
| ③ 같은 snapshot을 gzip으로 압축하면 | 1.9KB (약 1/6) |
| ③ PC가 snapshot을 만드는 시간 | 1.2ms~4ms |
| ⑤ 응답 압축(Content-Encoding) | **없음** |
| ⑤ 연결 재사용(keep-alive) 유지 시간 | PC 서버 5초(Node 기본값, 따로 설정 안 함) |
| ⑤ 새 HTTPS 연결 vs 재사용 (같은 PC 안) | 3.3ms vs 1.0ms |

### 원인 후보별 정리 (큰 순서)

**1. snapshot 500ms 묶음 + 50ms 갱신 대기 — 영향 큼 (체감 약 0.5~0.6초)**
- 근거: `main/remote/events.ts`의 `SSE_LIMITS.coalesceMs = 500`, `publish()`가 첫 값을 받아도 **바로 보내지 않고 타이머 500ms 뒤에** 마지막 값을 보냅니다(맨 앞 값부터 보내는 방식이 아님). 그 앞에 `office.ts`의 `scheduleEmit()` 50ms 대기가 한 번 더 있습니다. 승인 처리 → snapshot 반영이 실측 약 550ms입니다.
- 영향: 승인 카드가 사라지는 것, 직원이 "대기 → 일하는 중"으로 바뀌는 것이 모두 이만큼 늦게 보입니다. 휴대폰 데이터 속도와 상관없이 항상 생기는 지연입니다.
- 고칠 방법: 묶음을 "처음 값은 바로, 그 뒤 500ms 동안 온 것만 묶어서 한 번 더"(앞쪽 즉시 발송 + 뒤쪽 묶음)로 바꿉니다. 또는 사람이 누른 호출(decide·sendChat 등) 직후에는 묶음을 건너뛰고 즉시 보냅니다(`handleV2Call` 뒤에 `flush`). 부수 효과: 작업이 많을 때도 최대 초당 약 2회→앞쪽 즉시 + 뒤쪽 2회로 늘 뿐이라 데이터 부담은 작습니다(11KB × 연결 2개).
- 난이도: 낮음. `events.ts` 한 곳(약 10줄)과 시험 수정.

**2. 누르자마자 화면에 먼저 반영하는 처리가 없음 (휴대폰 화면 쪽, PC 쪽 근거만) — 영향 큼**
- 근거: 승인 버튼은 `window.office.decide()`만 부르고(`ApprovalTab.tsx:59`) 카드는 snapshot이 와야 사라집니다. 로컬 상태를 먼저 바꾸는 코드가 없습니다. 메시지 보내기는 입력창만 먼저 비우고 말풍선은 PC가 `chat` 이벤트를 보낸 뒤에야 나옵니다(`ChatPage.tsx` handleSend). 휴대폰은 "call 응답 → 이벤트/snapshot" 2번을 순서대로 기다리는 구조입니다.
- 영향: 원인 1의 지연 + 왕복 시간이 모두 화면에 그대로 드러납니다.
- 고칠 방법: 승인·반려는 누르는 즉시 카드를 "처리 중"으로 바꾸거나 숨기고, 실패하면 되돌립니다(앞서 만든 결재 카드의 `decideOutcome` 같은 방식). 메시지는 보낸 즉시 "보내는 중" 말풍선을 보여 주고 `chat` 이벤트로 확정합니다. **휴대폰 앱 쪽 작업이라 임안드 절과 함께 판단해 주세요.**
- 난이도: 중간(되돌리기·중복 방지 처리 필요).

**3. 연결을 5초만 재사용 + 압축 없음 + HTTP/1.1 — 영향 중간(추정, 실제 Wi-Fi 확인 필요)**
- 근거: `server.ts`가 `keepAliveTimeout`을 따로 설정하지 않아 Node 기본 5초입니다. 5초 넘게 가만히 있다가 누르면 연결이 끊겨 있어 TCP+TLS 핸드셰이크를 새로 합니다(같은 PC 안에서는 +2.3ms지만, 실제 Wi-Fi에서는 왕복 시간×2~3회로 **추정 60~300ms**). 응답 압축도 없습니다(snapshot 11.2KB → 1.9KB로 줄 수 있음).
- 영향: 승인·전송 같은 짧은 호출은 이미 작아서(응답 수십 바이트) 압축 효과는 작고, snapshot을 새로 받을 때(재연결·앱 복귀) 효과가 큽니다.
- 고칠 방법: `https.createServer` 뒤에 `server.keepAliveTimeout = 60_000`(헤더 타임아웃도 함께 조정), `/v2/call` 큰 응답(snapshot·기록)에 gzip 적용(요청 `Accept-Encoding` 확인). SSE(이벤트 스트림)는 압축하지 않습니다.
- 난이도: 낮음(keep-alive) / 낮음~중간(gzip, 응답 크기 한도·SSE 예외 처리).

**4. snapshot이 직원 한 명만 바뀌어도 전체를 다시 보냄 — 영향 작음(현재 규모)**
- 근거: 11.2KB, 직원 1명 0.9KB. 기록·대화는 snapshot에 들어 있지 않아(별도 호출) 쌓여도 커지지 않았습니다. PC가 만드는 시간도 1~4ms입니다.
- 영향: 직원 10명 정도에서는 느림의 원인이 아닙니다. 직원·업무 카드가 수십~수백 개가 되면 커질 수 있지만 이번에 쓸 만한 실측은 못 했습니다.
- 고칠 방법: 바뀐 직원만 보내는 부분 갱신(diff)은 규격 변경이 커서 지금은 권하지 않습니다. gzip(3번)이 먼저입니다.
- 난이도: 높음.

**5. PC 처리 자체 — 영향 없음**
- `/v2/call` 5~7ms, 인증·검사 코드는 sha256 비교뿐이라 가볍고(`auth.ts`), 처리 시간 한도(timeout)도 걸림돌이 아닙니다. 고칠 필요 없음.

### 확인 못 한 것
- **실제 휴대폰·Wi-Fi·Tailscale·인터넷 경로의 왕복 시간**: 같은 PC 안에서만 쟀습니다. 3번의 핸드셰이크 비용은 추정입니다. 휴대폰에서 `/v2/call` 시작~끝 시간을 찍어 보면 확정됩니다(임안드 절).
- PC가 AI 작업으로 바쁠 때(엔진 출력이 몰릴 때)의 응답 시간. 가짜 엔진이라 이 상황은 재현하지 못했습니다.
- 직원 수십 명·업무 수백 개일 때의 snapshot 크기.
- 휴대폰이 `/v2/events`를 끊고 다시 붙는 상황(앱 복귀)의 따라잡기 시간.

### 권장 순서
1. snapshot 묶음 방식 변경 (난이도 낮음, 효과 가장 큼, PC만 고치면 됨)
2. 휴대폰 화면의 즉시 반영 (임안드와 같이 결정)
3. keep-alive 60초 + gzip

## 휴대폰 쪽 (임안드 · 안드로이드)

조사만 했고 코드는 고치지 않았습니다. 코드만 읽었고 실기기 측정은 못 했습니다. 그래서 영향 크기는 모두 **추정**입니다.
본 곳: `android/.../net/PinnedTls.kt`, `net/RemoteClient.kt`, `web/EventStream.kt`, `web/WebShell.kt`, `web/BridgeProtocol.kt`, `app/src/renderer/mobile/{bridge,remoteOffice,install}.ts`, `app/src/renderer/store.ts`, 승인·채팅 화면.

### 한 번 누를 때 일어나는 일
버튼 → `window.office.decide/sendChat` → `bridge.request` → WebShell → `RemoteClient.v2Call`(`POST /v2/call`) → PC. 화면은 **응답으로 바뀌지 않고**, PC가 SSE로 보내는 `snapshot`·`chat` 이벤트가 와야 바뀝니다.
체감 지연 ≈ 새 연결 맺기 + PC 처리(5~7ms) + snapshot 묶음 대기(PC 절 약 0.55초) + 화면 다시 그리기.

### 원인 후보 (큰 순서)

**1. 호출마다 TCP+TLS를 새로 맺음 — 영향 큼(추정), 난이도 하**
- 근거: `PinnedTls.kt:73-75` `connectionPool(ConnectionPool(0, 1, SECONDS))` — 연결을 재사용하지 않습니다. 주석 이유는 "PC 서버가 쉬는 연결을 몇 초 뒤 닫아서"인데, v1 조회(30초·15분 간격) 기준 설정입니다. `v2Call`이 쓰는 `lanCallHttp`/`externalCallHttp`도 이 `pinnedClient`를 그대로 씁니다(`RemoteClient.kt:250-254`). `retryOnConnectionFailure(false)`.
- 영향: 버튼마다 TCP(1 RTT)+TLS(1~2 RTT)=약 2~3 RTT가 앞에 붙습니다. Tailscale 직접 연결(RTT 20~50ms)이면 0.1초 안팎, **중계(DERP, RTT 100~300ms)면 0.3~0.9초**. `hello`·`snapshot` 같은 부수 호출과 SSE 재연결에도 똑같이 붙습니다.
- 고칠 방법: v2 호출·이벤트용 클라이언트만 `ConnectionPool(2~3, 20~30초)`로 재사용하고(v1 조회용은 그대로), 끊긴 연결로 실패하면 **한 번 자동 재시도**합니다. `Idempotency-Key`(`WebShell.kt:396`)가 이미 있어 중복 처리되지 않습니다. 지문 고정은 연결을 맺을 때 확인되므로 재사용해도 약해지지 않습니다. **PC 절 3번(서버 keep-alive 5초 → 60초)과 짝으로 해야 효과가 있습니다.** 서버가 5초 뒤 닫으면 폰이 재사용을 시도해도 끊긴 연결에 걸립니다(그래서 재시도가 필요).
- 난이도: 하 (설정 한 곳 + 재시도 한 번)

**2. 누른 즉시 보이는 반응이 없음 — 체감 영향 가장 큼, 난이도 하~중**
- 근거: 승인 버튼(`ApprovalTab.tsx:59`, `InboxPage.tsx:135`, `ApprovalBand.tsx:23`, `ChatPage.tsx:591`)은 `void window.office.decide(...)`만 부릅니다. 눌림 표시(비활성·스피너)도, 카드를 먼저 치우는 낙관적 갱신도 없습니다. 채팅(`ChatPage.tsx:680-686`)은 입력칸만 비우고 `sendChat`을 `void`로 보내며, 내 말풍선은 PC의 `chat` 이벤트가 와야 나옵니다. `decide` 응답 값은 store에 반영되지 않습니다(`remoteOffice.ts`의 `call`).
- 영향: 1번 + PC의 0.55초 묶음 + 왕복이 **그대로 눈에 보이는 빈 시간**이 됩니다. 아무 변화가 없으니 느리다고 느끼고 다시 누르기 쉽습니다(중복 눌림 방어 없음).
- 고칠 방법: (a) 누르면 즉시 버튼 비활성+"처리 중" 표시(승인 id 기준 로컬 상태). (b) 승인·거절은 해당 승인을 store에서 먼저 지우고 실패하면 되돌려 안내. (c) 채팅은 임시 id의 "보내는 중" 말풍선을 바로 넣고 `chat` 이벤트의 같은 글이 오면 교체. (a)만 해도 체감이 크게 좋아집니다.
- 난이도: (a) 하 / (b) 중 / (c) 중

**3. snapshot마다 store를 통째로 갈아 끼워 화면이 넓게 다시 그려짐 — 영향 중간(추정), 난이도 중**
- 근거: `store.ts:156-167` `setSnapshot`이 `{...snap}`으로 staff·tasks·runs·승인 등 **모든 배열을 새 참조로** 바꿉니다. 내용이 같아도 새 객체라서 `useOffice((s) => s.staff)`처럼 배열을 구독한 컴포넌트(23곳 이상)가 전부 다시 렌더됩니다. 값 비교(structural sharing)가 없습니다. 또 셸은 snapshot 본문을 파싱해 다시 문자열로 만들고(`BridgeProtocol.kt:138-148`), 화면이 한 번 더 `JSON.parse`합니다(`bridge.ts`). snapshot은 직원 상태가 바뀔 때마다 옵니다.
- 영향: 중저가 기기에서는 승인 직후 snapshot 렌더가 카드 사라지는 시점을 늦추고 스크롤·입력이 끊깁니다. 실제 렌더 시간은 미측정(React Profiler로 재야 함). 크기는 11KB 정도라 파싱 자체는 작습니다(PC 절 측정).
- 고칠 방법: `setSnapshot`에서 이전 값과 비교해 같은 부분은 기존 참조 유지, 연속 snapshot은 프레임 단위로 묶어 마지막 것만 반영. 셸은 이벤트 JSON을 파싱하지 말고 문자열 그대로 끼워 넣기.
- 난이도: 중 (회귀 위험). 먼저 프로파일로 비중 확인 권장.

### 그 밖의 후보 (작거나 조건부)
- **4. SSE 재연결·복귀 시 전체 다시 받기 — 작음~중간(조건부), 난이도 중.** 앱이 백그라운드로 가면 스트림을 닫고(`onBackground`) 돌아오면 새로 맺습니다(1번 비용 포함). `Last-Event-ID`를 보내지만 PC가 놓친 구간을 못 채우면 `hello.resync=true` → 화면이 `snapshot`+`chatHistory`+`timeline`을 전부 다시 읽습니다(`install.ts:35-45`). 35초 무소식이면 끊고 재연결, 대기는 1·2·4…30초이며 앱 복귀·망 전환은 `reconnectNow()`로 바로 붙습니다. 평소 버튼 지연과는 별개로 복귀 직후 느려 보이는 원인입니다. 고치기: PC가 이벤트를 더 오래 보관(PC 절), 폰은 1번으로 재연결 비용을 줄이고 resync 때 `chatHistory`를 최근분만 받기.
- **5. 호출 동시 5개 한도와 첨부 변환 — 작음.** `V2_MAX_CONCURRENT=5` 세마포어(`RemoteClient.kt:79,356`). 화면 진입 때 `snapshot`·`chatHistory`·`timeline`·`hello`·사진이 몰리면 버튼 호출이 줄을 설 수 있습니다. 버튼류 호출용 슬롯을 따로 두면 됩니다. 첨부는 base64로 브리지를 지납니다(`toBase64`).
- **6. 셸 통로(bridge) 자체 — 작음.** `postMessage`는 JSON 문자열 한 번, WebShell이 코루틴에서 바로 처리, 요청마다 id로 매칭할 뿐 폴링·추가 대기는 없습니다. 이중 직렬화(3번)를 빼면 수 ms 수준(추정). 고칠 것 없음.

### Tailscale 중계(DERP) 여부 — 앱에서 아는 방법
- 지금 앱에는 직접/중계를 구분하는 코드가 없습니다(`isTailscale` 여부만 앎).
- 방법: ① **앱이 시간을 잰다**: `OkHttp EventListener`(`connectStart`·`secureConnectEnd`·`responseHeadersStart`)로 연결 맺는 시간과 첫 응답까지의 시간을 따로 기록해 진단 화면·로그에 표시합니다. 직접 연결은 대개 수십 ms, 중계는 100ms 이상이라 DERP 여부와 1번의 비용이 바로 숫자로 나옵니다(난이도 하). ② PC에서 `tailscale ping <휴대폰>`이 `direct`인지 `relay`인지 봅니다(앱 밖). 앱 안에서 Tailscale 상태를 읽는 방법은 없습니다. ③ 같은 와이파이면 QR의 `lan` 주소를 먼저 시도하고(2초 제한) 성공한 길을 기억합니다(`RouteMemory`). 길이 바뀌면 첫 호출이 2초 늦을 수 있습니다.
- DERP이면 1번의 비용이 2~4배로 커져서, 연결 재사용이 이 환경에서 가장 효과가 큽니다.

### 휴대폰 쪽 권장 순서
1. 누름 즉시 표시(2-a) — 가장 싸고 체감 최대.
2. v2 연결 재사용 + 1회 재시도(1) — PC keep-alive와 같이.
3. 앱에서 연결 시간 기록(DERP 확인) — 이후 병목을 숫자로 판단.
4. 낙관적 갱신(2-b·2-c)과 snapshot 렌더 줄이기(3)는 프로파일 결과를 보고.

### 확인하지 못한 것
- 실기기·실제 Tailscale 경로의 시간. 영향은 모두 코드에서 추정한 값입니다.
- React 렌더 시간(3번)과 snapshot 도착 빈도.
- 안드로이드 쪽 요청 시작~끝 시간 실측(PC 절이 요청한 항목) — 위 EventListener 기록이 있으면 바로 얻습니다.
