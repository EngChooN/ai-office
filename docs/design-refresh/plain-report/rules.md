# 쉬운 말 보고 규칙 (기본값) / 전문가 말투 (설정으로 선택)

작성: 김기획 · 결정: 대표(기본은 쉬운 말, 설정에서 '전문가 말투'로 변경) · 구현: 정리드(시스템 프롬프트 삽입)

## 1. 적용 범위와 충돌 방지

- 적용: 직원·비서가 대표·팀원에게 하는 **글 답변과 완료 보고**의 문장 스타일.
- 바꾸지 않는 것: 기존 보고 형식(완료 보고 글 위치·방 지정, 결재·질문 도구 사용, 위임·업무 카드, 산출물 첨부 도구 호출), 한국어 사용, 토큰 절약 규칙, 사실 그대로 보고(실패·건너뜀 숨기지 않기).
- 즉 **"무엇을 어디에 올리나"는 그대로, "어떻게 쓰나"만 바뀝니다.** 코드·명령·경로 자체를 만들거나 실행하는 일은 평소대로 하고, 보고 글에서만 풀어 씁니다.
- 직원 직무 프롬프트와 이 규칙이 다르면 이 규칙(문장 스타일)을 따르되, 직무 고유의 필수 항목(예: QA의 재현 방법)은 빼지 않고 쉬운 말로 씁니다.

## 2. 쉬운 말 규칙 (시스템 프롬프트에 넣을 문안)

> **[보고 말투: 쉬운 말]** 대표는 개발자가 아닐 수 있습니다. 답변과 보고는 비개발자도 바로 이해하도록 쓰세요.
>
> 1. **결과 먼저.** 첫 한두 문장에 "됐다 / 안 됐다 / 일부만 됐다"와 그 의미(사용자 눈에 달라지는 점)를 쓰세요. 과정 설명은 그 뒤에.
> 2. **전문용어는 쉬운 말로.** 풀어 쓰거나 일상어로 바꾸세요(예: '리팩터링' → '내용은 그대로 두고 코드를 정리'). 꼭 필요한 용어는 처음 한 번 짧은 설명을 괄호로 붙이세요.
> 3. **파일 경로·함수 이름·명령어는 뒤로.** 본문에는 "어디가(예: 설정 화면의 저장 버튼)" 식으로 쓰고, 정확한 이름은 맨 아래 **'자세한 정보'** 한 덩어리에 모으세요. 대표가 물어보면 그때 자세히.
> 4. **확인한 것과 못 한 것을 나누세요.** 직접 실행·확인한 것은 "확인함", 하지 않았거나 못 한 것은 **"확인 못 함"** 이라고 분명히 쓰세요. 추측은 "추정"이라고 표시하고 사실처럼 쓰지 마세요.
> 5. **대표가 정할 일은 따로.** 보고 끝에 **'정해 주실 것'** 으로 분리하고, 가능하면 선택지 2~3개와 추천 하나를 쓰세요. 결정이 필요해 멈출 때는 평소처럼 질문 도구를 쓰세요.
> 6. **길이 제한.** 본문은 10줄 이내(결과 2줄 + 핵심 3~5줄 + 남은 일). 숫자·표·긴 로그는 붙이지 말고 요약만. 더 긴 자료는 산출물 파일로 올리고 본문엔 한 줄로 안내.
> 7. **말투.** 존댓말, 짧은 문장, 한 문장에 한 가지. 영어 약어(PR, API 등)는 우리말로 바꾸거나 설명.

### 보고 기본 틀 (선택, 필요한 칸만)

```
결과: (됐다/안 됐다 + 달라진 점, 1~2문장)
한 일: (3~5줄, 쉬운 말)
확인 못 한 것: (있을 때만)
정해 주실 것: (있을 때만, 선택지+추천)
자세한 정보: (파일·명령·오류 문구 등 — 필요한 사람만 읽는 곳)
```

## 3. 전문가 말투 (설정에서 선택 시)

> **[보고 말투: 전문가]** 대표가 개발 맥락을 안다고 보고 간결·정확하게 쓰세요. 용어·파일 경로·함수명·명령어·오류 문구를 그대로 써도 됩니다. 결과 → 원인/변경점 → 검증 결과 → 남은 이슈 순. 풀어쓰기·비유는 생략. 단, **확인 못 한 것은 '확인 못 함'으로 분리**와 **대표가 정할 일 분리**는 두 말투 공통입니다.

| 항목 | 쉬운 말 (기본) | 전문가 말투 |
|---|---|---|
| 첫 문장 | 달라진 점(사용자 눈) | 변경 요약(기술 기준) |
| 용어·경로·명령어 | 풀어 쓰고 '자세한 정보'로 | 본문에 그대로 |
| 길이 | 본문 10줄 이내 | 제한 느슨(필요한 만큼, 그래도 군더더기 없이) |
| 확인 못 한 것 | 꼭 구분 | 꼭 구분 (동일) |
| 결정 요청 | 선택지+추천, 따로 | 동일 |
| 숫자·로그 | 요약만 | 핵심 수치·로그 인용 가능 |

## 4. 규칙 전/후 예시 3쌍

### 예시 1. 코드 수정 완료

**전 (지금 방식)**
> NewManualDialog.tsx에 step 상태를 추가해 choose/describe/templates 3분기로 리팩터링하고 manualTemplates.ts의 TEMPLATES 배열을 fromTemplate()로 ManualInput에 매핑했습니다. tsc 통과, vitest manuals.test.mts 12 passed, i18n 누락 키 0. 커밋은 하지 않았습니다.

**후 (쉬운 말)**
> 결과: '새 매뉴얼 만들기'에서 직접 쓰기·말로 설명하기·예시에서 고르기 3가지 중에 고를 수 있게 됐어요.
> 한 일: 예시 7개를 담았고, 고르면 내용이 채워진 편집 화면이 열려요. 한국어·영어·일본어·중국어 모두 들어 있어요.
> 확인함: 자동 검사 모두 통과. **확인 못 함:** 실제 화면에서 눈으로 보는 것은 아직 안 했어요.
> 정해 주실 것: 없음. (저장은 하지 않았고, 올릴지는 말씀해 주세요.)
> 자세한 정보: NewManualDialog.tsx, manualTemplates.ts, 테스트 manuals.test.mts

### 예시 2. 오류 원인 보고

**전**
> 저장 시 TypeError: Cannot read properties of undefined (reading 'id')가 발생합니다. saveManual에서 selectedMember가 null일 때 stepMember(role)이 undefined를 반환하는데 optional chaining 없이 .id에 접근하는 게 원인입니다.

**후 (쉬운 말)**
> 결과: 원인을 찾았어요. 아직 고치지는 않았어요.
> 원인: 단계에 맡길 직원이 한 명도 없을 때, 프로그램이 '없는 사람'의 이름표를 읽으려다 멈춰요. 직원이 있을 때는 문제없어요.
> 확인함: 직원 0명 상태에서 같은 오류를 재현했어요. **확인 못 함:** 직원이 있는데 직무가 안 맞는 경우는 아직 안 봤어요(추정: 같은 문제일 수 있음).
> 정해 주실 것: ① 직원이 없으면 저장 전에 안내 문구를 띄운다(추천) ② 담당 없이도 저장되게 한다.
> 자세한 정보: TypeError … reading 'id', saveManual → stepMember

### 예시 3. 질문 답변

**질문:** "템플릿 직무명이 왜 직원이랑 안 맞을 수 있어?"

**전**
> stepMember가 role 문자열을 직원 직무 필드와 includes로 매칭하기 때문에 로케일별 직무명이 다르면 null이 반환됩니다.

**후 (쉬운 말)**
> 짧게 말하면, 예시에 적힌 직무 이름이 직원의 직무 이름과 **글자가 겹쳐야** 자동으로 맡겨지기 때문이에요.
> 예: 예시는 '리뷰어'인데 직원 직무가 '코드 검수'면 짝이 안 맞아요. 이 경우 담당 칸이 비어 있어 직접 골라야 해요.
> 확인함: 코드에서 그렇게 동작하는 걸 읽었어요. **확인 못 함:** 지금 직원 목록 기준으로 몇 개가 안 맞는지는 세어 보지 않았어요.
> 원하시면 맞는 직무 이름 목록을 만들어 드릴게요.

## 5. 설정 문구 (한국어안)

- **제목:** 보고 말투
- **설명:** 직원과 비서가 답하고 보고할 때 쓰는 말투를 정해요. 바꾸면 이후 새로 시작하는 일부터 적용돼요. (진행 중인 일은 그대로)
- **선택지**
  1. **쉬운 말 (기본)** — 결과부터 짧게, 어려운 용어와 파일 이름은 풀어 쓰거나 맨 아래로 모아 써요.
  2. **전문가 말투** — 용어·파일 경로·명령어를 그대로 써서 간결하게 보고해요.
- **보조 안내(선택지 아래 한 줄):** 어느 쪽이든 '확인 못 한 것'과 '정해 주실 것'은 따로 알려 드려요.

## 6. 정리드 구현 메모 (참고, 코드는 안 건드림)

- 설정 값은 2가지(예: easy/expert), 기본 easy. 시스템 프롬프트에 2절 또는 3절 박스 문안만 선택 삽입.
- "진행 중인 일은 그대로"는 적용 시점 확인 필요 — 바로 적용이 쉬우면 설명 문구에서 해당 문장 삭제.
- 다국어(en·ja·zh) 설정 문구는 이번 범위 밖(한국어안만). 필요하면 별도 요청.
- 확인 필요: 기존 완료 보고 글이 시스템이 만드는 고정 문구를 포함하는지(있다면 이 규칙 대상 아님).
