# 워크스페이스 1단계 최종 설계 결정 (정리드, 2026-11-12)

근거: `impl-design-readable.md`(최가독), `impl-design-pattern.md`(박패턴), 한리뷰 Round 1 리뷰.

## 결론
**박패턴 안을 뼈대로 하고, 화면 재활용은 최가독 안을 붙인다.**
이유: 이번 기능의 가장 큰 위험은 "원격 창이 이 PC를 조작하는 것"이다. 이 위험을 구조로 막는 쪽이 박패턴 안이다. 화면 쪽 재사용은 최가독 안이 더 구체적이고 코드량이 적다.

## 쟁점별 결정

| 쟁점 | 채택 | 이유 |
|---|---|---|
| 창 구조 | PC마다 창 1개, 전환 시 위치·크기 이어받고 이전 창 숨김, **창마다 파티션 분리** (박패턴) | 두 안 모두 창 분리. 파티션 분리로 `localStorage`가 이 PC 것과 섞이지 않는다 |
| 통로 | 원격 창은 `ws:*`만, `office:*` 핸들러에 **보낸 창이 이 PC 창인지 검사** 추가 (박패턴) | 한리뷰 7번과 같은 지적. 검사가 없으면 원격 창이 이 PC를 조작할 수 있다 |
| 새 API 위치 | `OfficeApi` 밖 `officeWorkspaces` (박패턴) | 휴대폰 분류표·휴대폰 앱으로 번지지 않는다 |
| 쓰기 막기 | 메인 브리지에서 막고, `Record<OfficeMethod, 'read'\|'write'>`로 tsc가 누락을 잡게 함. 화면 비활성은 보조 (박패턴) | 최가독 안(렌더러 어댑터 한 곳)은 우회 가능하고 분류표 재사용 여부가 미정 |
| 쓰기 표 기본값 | 분류가 애매하거나 새로 생긴 메서드는 `write`로 둔다 (박패턴 보충) | 빠뜨려도 막히는 쪽으로 실패한다 |
| 실시간 연결 | **잠정** PC당 화면용 연결을 따로 엶 (박패턴). 0단계에서 "한 열쇠로 연결 2줄"이 안 되면 최가독 안(PeerManager 연결 나눠 받기)으로 전환 | 중계 코드 무수정이 회귀 위험이 낮다. 다만 0단계 결정에 달려 있음 |
| 렌더러 부트 | `remote/install.ts` 새로 만듦, `mobile/install.ts` 무수정 (두 안 같음) | 중복 약 40줄, 휴대폰 회귀 0 |
| PC 전용 잠금 | `IS_REMOTE_SCREEN` 신설 + 치환 목록 확인 테스트 (최가독) | tsc가 못 잡는 누락을 테스트로 잡는다 |
| 화면 부품 | 마법사 코드 입력·표시는 `PeerSection`의 `ClientPart`·`HostPart`, 드롭다운은 `PopMenu` 재사용 (최가독) | 새 코드 최소화 |
| 상태 판정 | `statusOf` 한 함수 + 표 테스트 (박패턴) | 드롭다운·띠·관리 목록·마법사가 같은 판정을 쓴다 |
| 버전 섞임 | 연결 직후 hello에서 프로토콜 버전·허락 확인, 통과 전에는 창을 열지 않음 (박패턴) | 한리뷰 5번 |
| 기존 데려오기 대체 | 추가 → 이전 → 삭제, 삭제는 다음 릴리스 (두 안 같음) | 진행 중 일을 끊지 않고 되돌릴 수 있다 |

## 채택하지 않은 주요 제안
- **렌더러 어댑터에서 쓰기 막기(최가독):** 렌더러는 원격 창이 통제하는 쪽이라 막는 지점으로 약하다. 보조 표시로만 쓴다.
- **PeerManager 연결 공유(최가독):** 지금은 중계 코드를 건드리게 된다. 0단계 결과에 따라 다시 판단한다.

## 0단계(강백엔)에 먼저 못박을 것
1. 화면 보기 열쇠가 받는 이벤트가 휴대폰과 같은 모양인지
2. 한 열쇠로 연결 2줄이 열리는지 (실시간 연결 결정이 여기에 달림)
3. hello에 프로토콜 버전과 허락 상태가 오는지
4. 화면 보기 열쇠에도 작업 폴더·결재 방식·자율 진행 막기가 그대로 적용되는지
