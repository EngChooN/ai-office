## 1. 사무실 장면만 찍는 방법

### 1-1. 지금 구조 (확인한 사실)
- 사무실 안 장면은 **Phaser 캔버스 하나**(`renderer/map/officeStage.ts`의 `new Phaser.Game`, `type: AUTO` → WebGL, `pixelArt: true`)에 그려집니다.
- 그 캔버스는 **위쪽 = 지도 영역(`mapW × mapH`, 기기 px)**, **아래쪽 = 직원 미니 뷰 칸**으로 나뉩니다(`canvasSize()`). 미니 뷰 칸은 CSS로 잘려 안 보일 뿐 캔버스엔 있습니다.
- 직원 이름표·말풍선·이모트는 **캔버스 안의 Phaser 글자**입니다(`IsoOfficeScene.ts` 897~901행, `setBubble()` 1321행). 캔버스 안에 화면 고정 HUD는 없습니다.
- 회사 레벨 카드, 층 미니맵, 꾸미기·확대 버튼, 사이드바, 결재 팝업은 모두 **캔버스 밖 DOM**입니다.
- 미니 뷰가 이미 `POST_RENDER`에서 WebGL 캔버스를 2D 캔버스로 `drawImage`해 복사합니다(`afterRender()`, `preserveDrawingBuffer` 없이 같은 프레임 안에서 읽음). **같은 길을 그대로 쓸 수 있습니다.**
- 건물 밖(외관) 장면은 별도 2D 캔버스(`OfficeMap.tsx`의 `canvasRef`)입니다. 1차 범위는 **건물 안 장면**으로 두고, 외관은 같은 방식(2D라 더 쉬움)으로 추가 가능합니다.

### 1-2. 두 방법 비교

| | A. 캔버스에서 바로 뽑기 (추천) | B. Electron `webContents.capturePage` |
|---|---|---|
| 개인 정보 | **DOM이 원천적으로 빠짐.** 남는 건 말풍선 글뿐 → 장면 쪽 플래그로 가림 | 창 픽셀을 그대로 찍음. 지도 영역만 잘라도 레벨 카드·미니맵·버튼·뜨는 팝업·토스트가 들어감 → 찍는 동안 숨기는 처리가 여기저기 필요 |
| 프레임 비용(실측) | 2700×1520 WebGL → 800×450 복사 + `getImageData` **프레임당 중앙값 5.0ms**(p95 6~10ms) | 1350×760 창 일부 **호출당 16~28ms** + IPC로 메인→렌더러 전달·BGRA 변환 |
| 프레임 타이밍 | 장면이 그린 바로 그 프레임 → 끊김 없음 | 비동기 호출이라 간격이 들쭉날쭉 |
| 화질 | 장면 기기 px에서 바로 축소, 워터마크를 같은 2D 캔버스에 덧그림 | 화면 배율·창 크기에 따라 달라짐 |
| 손대는 곳 | `officeStage`에 "녹화 대상" 등록 1곳 + 장면에 말풍선 가림 플래그 1개 | 메인 IPC + 렌더러의 숨김 처리 여러 곳 |

→ **A안.** B안은 "개인 정보가 빠진다"를 보장하려면 DOM 쪽을 계속 쫓아다녀야 해서, 새 오버레이가 생길 때마다 새는 구조입니다. A안은 캔버스 경계가 곧 개인 정보 경계라 **구조적으로 보장**됩니다.

### 1-3. A안에서 지켜야 할 것
- **지도 영역만 읽기:** `drawImage(game.canvas, sx, sy, sw, sh, …)`의 원본 범위를 `0..mapW × 0..mapH` 안의 16:9 영역으로 제한 → 아래 미니 뷰 칸은 안 들어감.
- **읽는 시점:** `POST_RENDER` 안(WebGL 버퍼가 지워지기 전). 미니 뷰 `afterRender()`와 같은 자리에 "녹화 대상"을 하나 더 두는 형태.
- **말풍선 글 가리기:** 말풍선은 캔버스 안이라 DOM 숨김으로는 안 됩니다. 장면에 `isRedacting` 같은 플래그를 두고 `setBubble()`에서 글만 `···`로 바꿉니다(시안 3장 ②와 일치). 같은 캔버스를 찍으므로 **녹화하는 동안 사용자 화면에서도 말풍선 글이 가려집니다** — 시안의 "녹화 중" 버튼 표시와 함께 자연스럽게 받아들일 수 있는 수준으로 판단. 내보내기 전용으로 한 번 더 그리는 별도 카메라는 GPU 비용이 두 배라 1차에선 비추천.
- **카메라 고정:** 녹화 중 이동·확대를 막거나 녹화 시작 시점 화면으로 고정. 아래 3장처럼 카메라가 움직이면 GIF가 10배 넘게 커집니다.
- **워터마크:** 축소한 2D 캔버스에 매 프레임 덧그린 뒤 `getImageData` → 결과물 100%에 들어가는 것이 **구조로 보장**(인코더 앞 단계).
- **PNG 1장:** 같은 경로로 1프레임만 뽑아 `canvas.toBlob('image/png')`. 원본 해상도(예: 기기 px 그대로) 저장 가능.
- **배율:** 픽셀 아트라 축소 시 `imageSmoothingEnabled`를 켜면 색이 섞여 팔레트가 늘고(=용량 증가), 끄면 글자가 깨질 수 있음. 장면 기기 px가 출력 폭의 정수배에 가깝게 맞춰 축소하는 편이 용량·선명도 모두 유리. 구현 때 두 설정을 실제 화면으로 비교해 정할 것.

## 2. GIF 인코딩 방식 비교

| 후보 | 위치 | 라이선스 | 앱 크기 증가 | 상태·특징 |
|---|---|---|---|---|
| **gifenc 1.0.3** | 렌더러(Worker 가능) | MIT | **약 9KB**(esm 빌드) | 빠름. 팔레트 양자화·투명 인덱스 지원. 2022년 이후 갱신 없지만 기능이 작고 완결돼 위험 낮음 |
| gif.js 0.2.0 | 렌더러(자체 Worker) | MIT | 약 30KB(본체 13KB + worker 17KB) | 오래 방치됨. NeuQuant 양자화라 느림. 프레임 차이 최적화 없음 |
| modern-gif 2.1.0 | 렌더러 | MIT | 압축 전 약 168KB | 2026년 갱신, Worker 내장. 대안 후보 |
| gifski | — | **AGPL-3.0** | — | **제외**(앱 라이선스 MIT와 충돌) |
| ffmpeg-static(메인 프로세스) | 메인 | **GPL-3.0** 바이너리 | **맥 arm64 45MB, 윈도 x64 81MB** | 품질·속도 최상이지만 크기·라이선스 부담이 큼 |
| ffmpeg.wasm | 렌더러 | 래퍼 MIT, 코어 GPL | 약 30MB | 무겁고 느림. 제외 |

→ **gifenc를 렌더러 Web Worker에서.** 메인 프로세스는 저장 위치 대화상자·파일 쓰기·`shell.showItemInFolder`(폴더 열기)만 맡깁니다.

### 2-1. gifenc에서 용량을 결정짓는 두 가지 (실측으로 확인)
1. **팔레트를 1번만 만들기:** 프레임마다 양자화하면 느리고(800·15fps에서 13.7초) 팔레트가 흔들려 깜빡임이 생깁니다. 첫 프레임(필요하면 몇 장 샘플)으로 255색 팔레트를 만들고 고정.
2. **이전 프레임과 같은 픽셀은 투명 처리:** 투명 인덱스 1칸을 남겨 두고, 안 바뀐 픽셀을 투명으로 바꾸면 LZW 압축이 극적으로 좋아집니다(같은 조건 14MB → 0.58MB). gifenc는 이걸 자동으로 하지 않으므로 **우리 코드에서 해야 하는 부분**입니다(10줄 남짓).

### 2-2. 구현 시 주의 (실측 중 발견)
- 렌더러에서 큰 버퍼 하나의 `subarray`로 프레임을 넘기니 **같은 인코딩이 86초**로 느려졌고, 프레임마다 별도 버퍼로 넘기니 **1.2초**였습니다. 캡처가 프레임마다 `getImageData` 새 버퍼를 주므로 자연스럽게 피해지지만, 리뷰 때 확인할 항목으로 남깁니다.
- **메모리:** 800×450 RGBA 150장을 모아 두면 216MB. 녹화하면서 Worker로 프레임을 넘겨 **바로바로 인덱스화·차이 처리·쓰기(스트리밍)** 하면 원본을 쌓지 않아도 되고, 녹화가 끝난 뒤 남는 일은 마무리뿐입니다.

## 3. 예상 용량·소요 시간 (10초, 16:9)

### 3-1. 측정 방법과 한계
- 실제 사무실 화면 캡처(`gif-export-design/office.webp`, 사이드바 제외 영역)를 640×360 / 800×450으로 줄여 바탕으로 쓰고, 그 위에 **앉아서 일하는 직원 8명(1px 흔들림), 걷는 직원 3명, 나타났다 사라지는 말풍선, 깜빡이는 모니터 6개**를 흉내 냈습니다.
- 실제 장면은 이보다 움직임이 많을 수 있습니다(꾸미기 소품 연출, 이모트 등). 그래서 **최악 경우로 "카메라가 천천히 계속 움직임"(모든 픽셀이 매 프레임 바뀜)**도 쟀습니다.
- 시간은 M1 Pro 기준입니다. 윈도 저사양 PC는 대략 3~4배로 봅니다(추정, 실측 아님).

### 3-2. GIF (gifenc, 공통 팔레트 + 차이 투명 처리)

| 폭·fps | 장면 | 프레임 | 용량 | 인코딩 시간 |
|---|---|---|---|---|
| 640 · 10fps | 사무실, 카메라 고정 | 100 | 0.36MB | 0.57초 |
| 640 · 15fps | 사무실, 카메라 고정 | 150 | 0.42MB | 0.92초 |
| 800 · 10fps | 사무실, 카메라 고정 | 100 | 0.49MB | 0.83초 |
| **800 · 15fps** | 사무실, 카메라 고정 | 150 | **0.58MB** | **1.08초**(Electron 렌더러 안 1.22초) |
| 800 · 15fps | 외관(밤), 카메라 고정 | 150 | 0.60MB | 1.70초 |
| 800 · 15fps | **카메라 이동(최악)** | 150 | **7.45MB** | 1.43초 |

비교용(같은 800·15fps 프레임):

| 방식 | 카메라 고정 | 카메라 이동 |
|---|---|---|
| gifenc 프레임마다 팔레트 | 14.2MB · 13.7초 | 14.3MB · 10.2초 |
| gifenc 공통 팔레트(차이 처리 없음) | 14.0MB · 0.87초 | 14.3MB · 0.78초 |
| ffmpeg GIF(palettegen + diff_mode=rectangle) | 0.53MB · 0.29초 | 8.9MB · 0.65초 |
| **MP4 H.264(ffmpeg x264, crf 20)** | **0.16MB** · 0.26초 | **0.27MB** · 0.35초 |
| MP4 H.264(Electron WebCodecs, 1Mbps) | 0.69MB · 0.32초 | — |

- gifenc + 차이 처리는 ffmpeg GIF와 **거의 같은 용량**(0.58 vs 0.53MB)입니다. ffmpeg를 넣을 이유가 없습니다.
- 캡처 자체(프레임당 약 5ms)는 녹화하는 10초 동안 실시간으로 일어나 기다리는 시간에 들어가지 않습니다. 사용자가 기다리는 건 **녹화 종료 → 파일 저장**입니다. 스트리밍 인코딩이면 1초 미만, 모아서 인코딩해도 맥 1~2초입니다.

### 3-3. 5MB를 넘을 때 줄이는 순서 (최악 경우 추정)
카메라가 움직인 7.45MB(800·15fps)를 기준으로 비례 추정하면:
1. 15fps → 10fps: 약 5.0MB
2. 폭 800 → 640: 약 3.2MB(10fps 기준)

→ **카메라 고정 + 이 두 단계 자동 강등**이면 최악에도 5MB 안에 들어옵니다. 시안의 "5MB를 넘어 화질을 낮춰 저장했어요" 문구와 맞습니다. 강등은 녹화를 다시 하지 않도록 **원본 프레임을 건너뛰기/축소해 재인코딩**하는 방식이어야 하므로, 스트리밍과 함께 쓰려면 Worker가 첫 결과가 5MB를 넘을 때만 다시 돌 수 있게 프레임(인덱스 배열, 800·15fps 기준 54MB)을 잠깐 들고 있어야 합니다. 카메라를 고정하면 실제로 강등이 일어날 일은 드물 것으로 봅니다.

## 4. MP4 대안

| | GIF | MP4(H.264) |
|---|---|---|
| 용량(800·15fps·10초) | 0.6MB(고정) ~ 7.5MB(이동) | 0.16 ~ 0.7MB, 카메라가 움직여도 거의 안 커짐 |
| 화질 | 256색 → 밤 장면 그라데이션에 띠가 생길 수 있음 | 색 제한 없음. 단 픽셀 아트 가장자리가 살짝 뭉개질 수 있음(비트레이트로 조절) |
| 올리는 곳 | 긱뉴스 본문·GitHub README·마크다운 어디든 `<img>`로 바로 재생 | X·링크드인·슬랙은 좋음. GitHub README는 따로 업로드 필요, 마크다운 이미지로는 안 됨 |
| 구현 | gifenc(9KB) | **WebCodecs H.264**(Electron 44에서 지원 확인, 추가 크기 0) + **mp4-muxer**(MIT, 압축 전 156KB) — 또는 `MediaRecorder('video/mp4;codecs=avc1')`도 지원 확인(라이브러리 0개, 단 출력 형식·키프레임 제어가 약함) |
| 플랫폼 차이 | 없음(순수 JS) | 인코더가 OS·빌드별로 다름(이번 맥 빌드는 OpenH264 소프트웨어 인코더). 윈도 실측 필요 |
| 라이선스 | MIT | H.264 특허는 OS/Chromium 쪽 인코더를 쓰는 한 앱이 따로 신경 쓸 부분 없음(ffmpeg 번들 안 함) |

→ **1차는 GIF만.** 기획 목적(긱뉴스 본문)에 GIF가 맞고, 카메라 고정이면 GIF도 충분히 작습니다. MP4는 X 등 영상 채널 요구가 확인되면 추가 — **프레임 수집·워터마크 경로는 공유하고 인코더만 바꿔 끼우도록** 인코더 부분을 분리해 두면 추가 비용이 작습니다.

## 5. 완료 기준 N 제안

| 기준 | 제안값 | 근거 |
|---|---|---|
| 10초 GIF 용량 | **5MB 이하** | 카메라 고정 실측 0.4~0.6MB로 8배 이상 여유. 최악(카메라 이동)도 fps·폭 자동 강등으로 5MB 안. 흔히 알려진 올릴 곳 한도(예: GitHub 마크다운 이미지 10MB, X 웹 GIF 15MB)보다 작음 — **정확한 한도는 '올릴 곳 한도 조사' 카드 결과로 확정** |
| 내보내기 소요 시간 | **녹화 종료 → 저장 완료 5초 이하**(녹화 10초 제외) | M1 Pro 실측 1.1~1.7초. 윈도 저사양 3~4배를 감안해 5초 |
| PNG 1장 | **1초 이하** | 1프레임 복사 + PNG 압축 |
| 녹화 중 화면 끊김 | 지도 fps 체감 저하 없음(프레임당 추가 작업 10ms 이하) | 캡처 p95 6~10ms, 인코딩은 Worker |

QA 측정 방법: 기준 PC(맥 1대 + 윈도 1대)에서 직원 5명 이상이 일하는 장면을 800·15fps로 10초 녹화 → 용량과 "버튼에 '만드는 중' 표시 → 완료 안내"까지 시간을 잰다. 카메라를 일부러 움직인 경우도 1번.

## 7. 남은 확인 사항
- **윈도 실측 없음:** 시간은 맥 기준이고 윈도 배수는 추정입니다. 구현 QA에서 윈도 기준 PC로 5초 기준을 확인해야 합니다.
- **용량은 흉내 낸 움직임 기준:** 실제 사무실(소품 연출·이모트 등)에서는 카메라 고정 수치보다 커질 수 있습니다. 5MB까지 8배 여유가 있어 기준 자체는 유지 가능하다고 봅니다.
- **녹화 중 말풍선이 사용자 화면에서도 가려짐**(1-3) — 시안과 함께 대표 확인 필요.
- **축소 방식(부드럽게 / 픽셀 그대로)**에 따라 이름표 글자 선명도와 용량이 달라짐 — 구현 때 실제 화면으로 결정.
