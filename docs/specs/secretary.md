## 2. 도구 분류 (OfficeApi 84개)
- **조회(바로)**: 비서가 바로 호출하고 결과로 답한다.
- **변경(확인 카드)**: 비서는 "제안"만 만들고, 사용자가 카드에서 [실행]해야 앱이 실행한다. 비서 세션은 이 메서드를 직접 부를 수 없다(도구 자체가 "제안 만들기"만 한다).

## 3. 확인 카드
### 3-1. 기본 모양
```
┌ 이렇게 할까요? ─────────────────────────┐
│ 1. 팀 만들기 — "개발팀"                  │
│ 2. 직원 고용 — 프론트엔드 개발 · [모델 ▾] · [작업 폴더 ▾] │
│ 3. 팀 배치 — 새 직원 → 개발팀            │
│ ⚠ 주의할 점 (있을 때만)                  │
│                [취소]  [고치기]  [실행]  │
└──────────────────────────────────────┘
```
- 제목: "이렇게 할까요?" (단계 1개면 "이걸 할까요?")
- 단계마다: 번호 · 하는 일(쉬운 말 동사) · 대상 · 핵심 값. 메서드 이름·영어는 보이지 않는다.
- 위험도: 보통(기본) / 주의(노란 테두리 + 한 줄 이유) / 위험(빨간 테두리 + "되돌릴 수 없어요" + 버튼 이름을 [실행] 대신 동사로, 예: [퇴사시키기]).
- [고치기]: 카드 값(이름·모델·폴더 등)을 그 자리에서 수정. 대화로 "모델은 소넷으로" 하면 비서가 카드를 새로 만든다(이전 카드는 "바뀜"으로 흐리게).
- [실행] 후 카드가 결과 목록으로 바뀐다: 단계마다 ✓ 완료 / ✕ 실패(이유) / – 건너뜀.
- 카드는 한 번만 실행된다(두 번 누름 방지, 중복 실행 시 무시). 10분 지나면 "오래된 제안이에요. 다시 확인할까요?"로 바뀌어 [실행] 비활성(그사이 상태가 바뀌었을 수 있음).

### 3-2. 여러 단계를 한 카드로 묶기
- 비서는 "제안" 하나에 **단계 목록**을 담는다. 앞 단계 결과를 뒤 단계가 쓰면 **참조**로 적는다(예: 3단계의 직원 = 2단계에서 만든 직원, 팀 = 1단계에서 만든 팀). 실제 id는 실행 중에 채운다.
- 실행 순서: 위에서 아래로 차례대로. **앞 단계가 실패하면 뒤 단계는 건너뛴다**(참조가 비기 때문). 이미 된 단계는 자동으로 되돌리지 않는다. 결과 목록에 "1번은 됐고 2번에서 멈췄어요. 2번부터 다시 할까요?" + [이어서 하기].
- 한 카드 최대 **8단계**. 넘으면 비서가 카드를 나눠 제안.
- 실행 전 검사(카드 만들 때 미리): 이름 겹침(같은 팀 이름 존재), 대상 없음(퇴사한 직원), 인원 상한(회의 8명) → 카드에 ⚠로 표시.
- 단계 안에 확인 카드가 필요 없는 조회는 넣지 않는다(카드는 바꾸는 일만).

### 3-2-1. 묶음 단계 (8단계를 넘는 정리 작업)
- 같은 성격의 변경이 많으면 한 단계에 묶는다: `{ method: "batch", label: "오래된 카드 닫기", items: [{ method, args, label? }, …] }`. OfficeApi 메서드가 아니라 카드만의 형식이다(`BATCH_METHOD`·`BATCH_GUIDE` — shared/secretaryTools.ts).
- 항목은 변경 메서드만, **40개까지**(`BATCH_ITEMS_MAX`). 앞 단계 `$n` 참조 불가, 묶음 단계를 뒤 단계가 참조하는 것도 불가(결과가 하나가 아니므로). 묶음 안 묶음 불가. **위험 등급(퇴사·팀/랩 없애기·매뉴얼 지우기)은 묶을 수 없다** — 한 번 눌러 여러 개가 실행되면 권한을 넓히는 셈이라 하나씩 카드로.
- 카드: 항목마다 체크 — 체크를 풀면 그 항목을 뺀다. [실행] 때 `secretaryRun(cardId, { excluded: { 단계번호: [항목번호…] } })`(모두 1부터, 휴대폰 v2도 같은 필드). 모두 빼면 [실행] 비활성.
- 실행: 항목을 위에서 아래로. **한 항목이 실패해도 나머지 항목은 한다**(서로 기대지 않는 정리라서). 하나라도 실패하면 그 단계는 실패 → 뒤 단계 건너뜀. [이어서 하기]는 실패한 항목만 다시 하고, 뺀 항목은 계속 뺀다. 모두 뺐으면 단계는 건너뜀.

### 3-2-2. 비교 보기 (원문 ↔ 수정본 · 전 ↔ 후 그림)
- 확인 카드에 `compares: { kind: "text"|"image", label, before, after }[]`를 붙일 수 있다(최대 4개). **내용은 앱이 실제 값으로 만든다** — 모델이 적은 글은 넣지 않는다(카드 본문 규칙과 같다).
  - 글: 카드를 만들 때 `DeskDeps.compareOf(steps)`가 붙인다. 지금은 매뉴얼 저장(지금 본문 ↔ 새 본문, 새 매뉴얼은 빈 원문)·업무 지침·업무 카드 설명·랩 목표를 바꾸는 단계. 묶음 항목도 펼쳐서 본다. 한쪽 20,000자까지.
  - 그림: 오래 걸리므로 카드를 만든 뒤 `SecretaryDesk.attachCompares(cardId, compares)`로(실행 전 카드에만). `data:image/png|jpeg|webp;base64`만, 한 장 400,000자까지 — 상태가 휴대폰까지 가므로.
- 카드가 끝나면(완료·취소·만료·바뀜·내용 바뀜) 그림은 지운다(글 비교는 남긴다). 화면에는 "끝난 카드라 그림은 지웠어요".
- 화면: 넓으면 나란히, 좁으면(휴대폰) 위아래. 지운 말은 취소선, 더한 말은 밑줄(첨삭 카드와 같은 표시 — `CompareView.tsx`).

### 3-2-3. 매뉴얼 읽기·합치기와 직원 관리
- 매뉴얼 본문은 비서 도구 `read_manual(name, scope?, projectDir?)`로 전체를 읽는다(2만 자까지·단계·경로 포함). `listManuals`는 목록용 한 줄뿐이다. 글 비교(`compareSteps`, `secretaryCompact.ts`)는 `saveManual`(고치기는 `previousPath`, 같은 이름·범위 덮어쓰기는 그 매뉴얼이 원문)과 `deleteManual`(지울 본문 ↔ 지움)에 붙는다. 합치기 = `saveManual`(새 매뉴얼) + `deleteManual`(원본)을 한 카드로 — 위험 등급.
- 직원 관리: 업무 지침 점검은 `staff_detail` → 고칠 점 정리 → `updateStaff({ systemPrompt })`(비교 카드). 예약 업무는 `overview(section: "schedules")`로 조회, 없으면 `saveSchedule`(새 UUID)·`deleteSchedule`. 참고 문서는 `setRefDocs`(목록 전체), 장비는 `equipmentCatalog` 조회 후 `setEquipment`(바꿀 칸만 고친 전체 객체, 도구 허용·차단 목록은 그대로). 카드를 만들 때 결재 없이 쓰는 도구가 늘거나 막은 도구가 풀리면 경고한다. 분류·위험 등급은 그대로다.

### 3-2-4. 사무실 꾸미기 (가지고 있는 가구만, 0.13.0)
- 변경으로 옮긴 것: `placeItem`·`moveItem`·`storeItem`·`placeGridItem`·`moveGridItem`·`setGridItemOn`·`stowAllGrid`(주의)·`restoreGridItems`. 제외로 남긴 것: `buyItem`·`applySurface`·`claimMission`·`setGear` — 부탁받으면 이유 한 줄 + [상점 열기](#view=shop)(`EXCLUDE_HINTS`·`excludeMessage`, 지침에도 같은 말).
- 비서 도구: `office_layout(floor?)` 층마다 놓인 가구(uid·이름·칸·방향)와 서랍 · `arrange_office(floor?)` 알아서 배치 카드를 바로 올림 · `undo_stow()` 마지막으로 치운 가구 되돌리기 카드를 다시 올림.
- 카드 그림: 꾸미기 단계가 든 카드에는 `compareOf`가 그 층의 **지금 ↔ 실행한 뒤 평면도**(PNG, 층마다 한 쌍, 2개 층까지)를 붙인다(`decorCompares`·`renderFloorPlan` — main/secretaryDecor.ts). 몇 ms라 `attachCompares`를 쓰지 않고 카드를 만들 때 바로. 위에서 내려다본 도면이고 위·왼쪽이 뒤 벽, 색 이름은 이름표에(파랑 책상·남색 의자·주황 소파·초록 벽 가구, 회의실 하늘색·계단 회색 줄·출입구 노랑). 그림 안 색이라 화면 테마와 상관없다.
- "가구 다 빼줘": `stowAllGrid(floor, keepSeats)` 한 단계(0 = 건물 전체). 대표가 책상·의자까지라고 하지 않으면 `keepSeats: true`. 카드가 끝나면(완료·실패) 앱이 치운 가구 목록으로 **되돌리기 카드**와 안내 한 줄을 바로 올린다(`Secretary.offerUndo`). 10분이 지나 만료되면 "되돌려줘" → `undo_stow`. 기록은 메모리에만(앱을 끄면 사라짐).
- "알아서 배치해줘": `autoArrange(shop, level, floor)`(shared/iso/autoArrange.ts)가 안을 만들고 `arrangeSteps`가 카드로 — 1단계 그 층 `stowAllGrid(floor, false)`, 2단계부터 `placeGridItem` 묶음(40개씩, 8단계를 넘는 만큼은 서랍에 남김). 안의 순서대로 놓을 때마다 `canPlace`(메인 저장 직전과 같은 검사: 바닥 밖·고정 칸·겹침·소유·레벨·길 막힘)를 통과한 것만 넣었으므로 같은 순서로 실행하면 그대로 들어간다. 놓을 가구 = 그 층에 있던 것 + 서랍.
  1. 구역(휴게실·탕비실 등) 사각형 안의 가구는 제자리. 다른 가구는 구역 칸에 두지 않는다.
  2. 책상(2×1)·의자 짝: 지금 그 층의 책상·의자 수만큼, 의자가 책상을 보게(`seatsOf` hasDesk). 기본 자리와 같은 줄 간격(통로·의자·책상 3줄, 책상 3개마다 빈 칸)으로 뒤쪽부터, 왼쪽 벽에서 2칸 띄워서. 짝이 없는 책상·의자는 서랍에.
  3. 책상 구역(+통로 1칸)과 출입구 앞은 비운다. 나머지는 벽 가구(뒤·왼쪽 벽을 등지게, 서로 띄워서) → 러그(앞 왼쪽) → 소파(러그를 보게) → 놀이 가구(앞 오른쪽) → 그 밖 → 작은 소품(벽가에 흩어서). 먼저 둘레 한 칸을 띄운 자리, 없으면 붙여서. 실내 가구(벽 가구·러그·그 밖)는 야외 칸에 두지 않는다.
  4. 바닥(고정 칸 뺀 칸)의 50%를 넘게 채우지 않는다(러그 제외). 못 놓은 가구는 서랍에 남기고 비서가 개수로 알린다.
- 실행 뒤 가구 uid가 새로 생기므로 켜 둔 소품은 꺼진 상태로 놓인다. 되돌리기는 새 배치를 먼저 치운 뒤 원래 uid·켜짐 그대로 되놓는다.

### 3-3. 고용할 때 작업 폴더·직무·모델 정하기
| 값 | 정하는 법 | 카드 표시 |
|---|---|---|
| 직무 | 사용자 말에서 추출("프론트 개발자" → 프론트엔드 개발). `listAgentTemplates`에 맞는 정의가 있으면 그걸 추천 | 드롭다운: 추천 직무 + 불러온 정의 + 직접 입력 |
| 작업 폴더 | 기본 **"지정 없음"**(지시한 프로젝트로 가서 일함). 말에 프로젝트가 나오면 그 랩·최근 쓴 폴더를 추천 | [지정 없음 ▾] 목록: 지정 없음 / 랩 프로젝트 폴더들 / 최근 폴더 / **[폴더 고르기…]**(누르면 PC 폴더 선택 창 — 비서가 아니라 사용자가 고름) |
| AI 모델 | 기본은 앱 기본값. 직무가 리뷰·기획이면 기본, 단순 반복이면 가벼운 모델을 "추천"으로만 표시 | 드롭다운 + 한 줄 설명(빠름·저렴 / 똑똑함) |
| 이름·모습 | 이름은 직무 기반 제안, 모습은 직무에 맞춰 무작위(업무 모드면 이니셜) | 이름 칸 수정 가능 |
| 결재 방식·팀 | 결재 방식은 기본 "모두 결재". 팀은 말에서 추출 | 카드 값 |
- 사용자가 값을 말하지 않으면 **묻지 않고 기본값으로 카드를 만든다**(카드에서 고치면 되므로 대화가 짧아짐). 단 작업 폴더를 "지정"해야만 하는 상황(직원이 커밋·변경 탭을 써야 함)이면 ⚠로 알린다.

## 4. 첨삭 흐름
1. 대상 확인: "오큐에이 업무 지침"처럼 대상이 하나로 정해지지 않으면 후보를 보여 고르게 한다.
2. 원문 읽기(조회 도구) → 수정본 생성.
3. **비교 화면**:
   - 넓은 화면: 왼쪽 원문 · 오른쪽 수정본, 바뀐 부분 강조(지운 것 취소선, 더한 것 밑줄).
   - 좁은 화면(폰 v2 포함): 위아래 배치 + [바뀐 곳만 보기] 토글.
   - 위에 "바꾼 이유" 최대 3줄.
4. 버튼: **[적용]** · **[일부 적용]** · **[다시 다듬기]**(요청 추가 입력) · **[취소]**.
5. **부분 적용**: 바뀐 덩어리(문단·목록 항목 단위)마다 체크박스, 기본 전부 체크. 체크한 덩어리만 원문에 반영해 결과 미리보기 → [이대로 적용].
6. [적용]은 확인 카드와 같은 경로로 실행(`updateStaff`·`updateTask`·`saveManual`·`updateLab`). 실행 직전 원문이 그사이 바뀌었으면 "그사이 내용이 바뀌었어요. 다시 비교할까요?"로 멈춘다.
7. 적용 후 "되돌리기"는 1차 범위 밖. 대신 적용 전 원문을 대화 기록에 남겨 사용자가 복사할 수 있게 한다.
- 대상: 업무 지침(직원), 기획안·업무 카드 설명, 매뉴얼 본문·단계 설명, 랩 목표, 고용 정보(직무 문구). **코드 파일은 대상 아님.**

## 5. 자동결재 중 대신 답하기 규칙
### 5-1. 답할 질문 vs 아침까지 둘 질문
비서는 직원 질문을 받으면 아래 순서로 판정한다. **애매하면 둔다.**
| 판정 | 조건 | 예 |
|---|---|---|
| **답한다** | 기획서·업무 카드·참고 문서·매뉴얼·이전 대화에 근거가 있다 | "버튼 색은 기존 토큰 써도 되나요?" → 기획서에 "기존 토큰 사용" 있음 |
| **답한다** | 되돌리기 쉬운 진행 방식 선택(이름 짓기, 순서, 작은 범위의 기본값) | "테스트 파일 이름 a/b 중 뭐로?" |
| **둔다** | 대표의 결정·취향·우선순위가 필요(기획서에 "확인 필요"로 적힌 항목 포함) | "1차에 단체방 넣을까요?" |
| **둔다** | 비용·외부 전송·삭제·배포·보안 정책·권한 확대 | "프로덕션에 배포할까요?", "API 키 어디 둘까요?" |
| **둔다** | 범위를 바꾸는 질문(기능 추가·제외), 일정 약속 | "이것도 같이 할까요?" |
| **둔다** | 근거를 찾지 못함 | — |
- **둔** 질문에는 직원에게 짧게 답한다: "대표님 확인이 필요해서 아침에 답드릴게요. 그동안 다른 부분을 먼저 진행해 주세요." (직원이 멈추지 않고 할 수 있는 일을 계속하게)
- 기존 고정 답 `AWAY_ANSWER`는 비서가 꺼져 있거나 비서 호출이 실패했을 때의 **대체 답**으로 남긴다.
- 결재(권한 요청)는 기존 자동결재 규칙(위험 명령·외부 전송은 기다림)을 그대로 따른다. 비서는 **질문에만** 관여한다.

### 5-2. 기록과 요약
- 대신 답할 때마다 기록: 시각, 직원, 질문 원문, 판정(답함/둠), 답 원문, **근거**(문서 이름·문단 또는 "근거 없음").
- 저장: 자동결재 기록(`autoApproveLog`)에 "비서 답변" 종류로 합친다(대신 처리한 수의 `answered`와 일치).
- 아침 요약(대표가 돌아왔을 때 또는 자동결재 기간 끝): 
  ```
  밤사이 비서가 질문 5개를 받았어요.
  · 답한 질문 3개 — [펼치기] (직원 · 질문 · 내 답 · 근거)
  · 기다리는 질문 2개 — [지금 답하기]
  ```
  답한 질문마다 [다르게 답하기]: 대표가 다른 답을 주면 그 직원에게 "대표님 정정: …"으로 전달.
- 기다리는 질문은 결재함 "질문"에도 그대로 남아 있다(비서가 지우지 않음).

## 6. 비서 지침 초안 (시스템 프롬프트)
```
당신은 Claude Office의 비서입니다. 대표(사용자)가 말로 앱을 쓰도록 돕습니다.

말투
- 앱 문구 규칙을 따릅니다: 개발을 모르는 사람이 바로 알 수 있게 씁니다. 파일 경로, 프로그램·라이브러리 이름, 영어 약어, 함수 이름은 쓰지 않습니다. 꼭 필요하면 쉬운 말 뒤 괄호로 한 번만 씁니다.
- "~해요"체로 짧게 답합니다. 결론을 먼저, 근거와 방법은 뒤에. 목록은 3~5개까지.
- 화면이 있으면 링크를 함께 줍니다.

할 수 있는 일
- 사용법 안내(근거: 매뉴얼·사양·업데이트 소식), 현황 요약, 조언·첨삭, 조직 진단은 바로 답합니다.
- 무언가를 바꾸는 일은 직접 하지 않고 "제안"을 만듭니다. 제안은 확인 카드로 보이고, 대표가 [실행]을 눌러야 실행됩니다. "했어요"라고 말하지 말고 "이렇게 할까요?"라고 말합니다.
- 코드는 고치지 않습니다. 코드 일은 맞는 직원에게 맡기자고 제안합니다.

정직
- 모르는 것은 모른다고 답합니다. 앱에 없는 기능, 확인할 수 없는 사실을 지어내지 않습니다.
- 못 하는 요청에는 "못 해요"로 끝내지 않고 ① 왜 못 하는지 한 줄(비서가 쓸 수 없는 기능·대표가 직접 정하는 일·앱에 없는 기능) ② 대신 할 방법 — 어느 화면·메뉴에서 하면 되는지 링크와 함께 답합니다. (실제 문구는 main/secretary.ts SYSTEM_PROMPT)
- 숫자(비용·개수·시간)는 도구로 조회한 값만 씁니다. 조회하지 못했으면 "지금 확인하지 못했어요"라고 말합니다.
- 조회 결과와 대표의 말이 다르면 조회 결과를 보여 주고 확인을 부탁합니다.

대신 답하기(자동결재 중)
- 기획서·업무 카드·참고 문서·매뉴얼에 근거가 있을 때만 답하고, 답할 때 근거를 함께 남깁니다.
- 대표의 결정이 필요한 질문, 비용·외부 전송·삭제·배포·보안·권한·범위 변경 질문, 근거가 없는 질문은 답하지 않고 아침까지 둡니다. 애매하면 둡니다.

하지 않는 일
- 결재 규칙을 우회하거나 직원 권한을 몰래 넓히지 않습니다.
- 연결·보안 설정, 상점·꾸미기, 코드 저장·공유는 대신 하지 않습니다.
- 개인정보·비밀값(토큰, 비밀번호)을 답이나 기록에 옮기지 않습니다.
```

## 7. 기타
### 7-1. 비용 표시
- 비서 사용량은 직원과 같은 방식(토큰·추정 비용)으로 기록하되 **"비서" 줄로 따로** 표시한다.
  - 급여 명세서: 직원 표 맨 아래 "비서" 행(아바타 대신 비서 아이콘). 일·주·월 토큰 한도 합계에는 **포함**(같은 계정 사용량이므로).
  - 대시보드: 오늘 사용량 타일 아래 "그중 비서 n" 한 줄.
  - 비서 페이지: 대화창 위에 "오늘 비서 사용량 n" 작게. 한 답이 길게 도구를 여러 번 쓰면 답 아래 회색으로 "이번 답 n 토큰"(설정에서 끌 수 있음).
- 자동결재 중 대신 답하기 사용량도 비서 사용량에 포함.
- 비서는 예산(한도) 100%에 닿으면 조회·사용법 답만 하고 "한도에 닿아 새 작업 제안은 쉬어요"라고 안내(확인 필요 Q4).

### 7-2. 대화 보관 기간
- 대화는 로컬 DB에 **30일** 보관 후 자동 삭제(확인 필요 Q3).
- 확인 카드 실행 기록, 대신 답하기 기록은 감사 목적으로 **자동결재 기록과 같은 기간**(별도 정책 없으면 90일) 보관.
- 비서 페이지에 [대화 지우기](전체) 버튼. 지워도 실행 기록은 남는다.
- 비서 세션 문맥은 새 대화를 시작하면 비운다(이전 대화를 매번 다 싣지 않아 비용 절약). 오래된 대화는 요약만 이어 붙인다.
