# 회의·협업 흐름 개선 스프린트 — 기획서 (초안)

> 작성: 김기획(PO) · 2026-10-24 · 기준 0.10.1
> 상위: 회의·협업 흐름 개선 스프린트 — 준비 단계 3/4 (기획서)
> 선행 문서: [meeting-decisions.md](meeting-decisions.md)(저장 구조, 강백엔) · [meeting-decisions-design.md](meeting-decisions-design.md)(토큰·펼침, 이디자)
> 이 문서는 **기획서 초안**이다. 코드는 고치지 않았다. 구현은 리드 취합 → 대표 승인 뒤 별도 기획안으로 진행한다.

## 0. 요약

1. 회의 결정은 **저장된 `MeetingDecision` 하나가 원본**이다. 회의 화면 강조, 회의 결과 카드, 기획안 초안이 모두 `shared/meetingDecisions.ts`의 같은 함수(`decisionView`·`decisionLines`)로 읽는다. 회의록 쓰는 AI는 결정 내용을 다시 쓰지 않는다.
2. 회의가 끝나면 앱이 **기획안 초안**(결정 사항(직접)·위임 결정·할 일과 담당 제안)을 자동으로 만들어 회의 결과 카드에 붙인다. 리드는 이 초안으로 순서와 세부 내용을 다듬어 올리고, **제출은 지금처럼 대표 승인**을 거친다. 결정 두 섹션은 앱이 채우며 리드가 고칠 수 없다.
3. 같은 업무가 리드에게 두 번 전달되는 버그는 **`assignTask`가 이미 진행 중인 같은 카드를 다시 보내는 것**이 유력한 원인이다(재현 확인 필요). 수정을 하위 업무 1번으로 먼저 처리한다.

## 1. 배경과 현재 상태

| 항목 | 지금 (코드 근거) | 문제 |
|---|---|---|
| 결정 저장 | `MeetingDecision` = { id, askedBy, askedByName, question, options, answer, ts } (`shared/types.ts:318`) | 직접인지 위임인지 구분할 필드가 없다. 위임하면 누가 무엇으로 정했는지 남지 않는다. 회의를 끝내 풀린 결정도 `''`라서 위임과 구분되지 않는다 |
| 질문 원문 | `splitDecision`(`main/office.ts:2266`)이 `[결정 요청]` 앞 글자를 버리고 그 줄을 발언에서 지운다 | 질문 앞부분이 잘린다. 표시를 말로 언급만 해도 결정 요청으로 잡힌다(강백엔 문서 2절의 실제 사례) |
| 결정 표시 | `DecisionBox`(`renderer/features/MeetingPage.tsx:241`)가 `answer`를 직접 해석한다 | 위임은 "알아서 정하라고 했어요"로만 보이고 결정자가 없다 |
| 회의 종료 | 진행자가 리드면 `meetingResultCard`(`shared/planTasks.ts:37`) 한 장을 리드에게 배정한다(`office.ts:1937`). 시작은 대표가 보드에서 누른다 | 카드에는 회의록 글만 들어 있다. 결정은 회의록 AI가 쓴 자유 문장이고, 리드가 기획을 처음부터 쓴다 |
| 기획안 제출 | `propose_plan`(`office.ts:998`)은 리드가 받은 업무가 여러 개면 `task` 제목을 요구한다(`office.ts:1019`) | 같은 카드가 두 번 전달되면 "업무를 여러 개 받았습니다"에 걸려 제출이 막힌다 |

### 1-1. 두 번 전달 버그 — 코드에서 본 원인 (재현 확인 필요)
- `assignTask`(`office.ts:1714`)는 **다른** 카드를 하는 중이면 대기열에 넣지만(`o.taskId !== taskId`), **같은** 카드를 이미 하는 중인지는 확인하지 않는다. 그래서 같은 카드로 다시 불리면 `instruct`가 다시 나가고, `origins`에 같은 `{ kind: 'task', taskId }`가 두 번 쌓인다(`office.ts:492`).
- `propose_plan`의 받은 업무 목록(`office.ts:1015`)은 `origins`를 그대로 펼치므로 같은 카드가 두 번 들어가 `myTasks.length > 1`이 된다. 제목을 적어도 `named`가 2개라 `named.length !== 1` 쪽에서 다시 막힌다(`office.ts:1017`).
- 같은 카드로 다시 불릴 수 있는 길: 보드의 시작 버튼(`BoardPage.tsx:305·443`, 상태 확인 없음), 랩 화면(`LabSection.tsx:239`), "모두 시작"(`startTasks`, `todo`만 거름), 대화 뒤 다시 맡기기(`resumeStopped`, `office.ts:655`), 대기열(`office.ts:641`), 비서의 `assignTask`.
- 이번 회의 결과 카드에서 실제로 어느 길이었는지는 **확인 필요**. 수정은 길과 상관없이 막는 쪽으로 한다(6절 T1).

## 2. 목표 흐름 — 보이고 → 기록되고 → 다음 업무로

```
[회의 중]  직원 발언에 "[결정 요청]" 줄  ─▶ 질문 전문 + raw 저장, 회의 멈춤
              │
              ▼
[보이고]   회의 화면·결재함 DecisionBox: "답 대기"(노랑, 질문 펼친 채)
              │ 대표가 답함                     │ "알아서 정해"              │ 회의 끝내기
              ▼                                 ▼                            ▼
[기록되고] kind=direct, 결정자=대표        kind=delegated, 진행자(리드)가    endedByMeeting
           "직접 결정"(초록)               바로 한 번 정함 → choice·결정자    "답하지 않음"(강조 없음)
                                           "위임 · 정리드"(주황 라벨)
              │                                 │                            │
              └──────────────┬──────────────────┴────────────────────────────┘
                             ▼  다음 발언 맥락도 decisionLines(최종 선택값 포함)
[회의 끝]  회의록(AI: 결론·할 일) + 앱이 만든 결정 블록(decisionLines)
                             ▼
[다음 업무로] 회의 결과 카드 = 기획안 초안(결정 직접 / 위임 결정 / 답하지 않음 / 할 일·담당 제안)
              → 리드 배정 → 리드가 순서·세부를 다듬어 propose_plan (결정 섹션은 앱이 고정)
              → 결재함 "기획 확인"에서 대표 승인 → 하위 업무 카드 생성·순서대로 진행 → 취합 보고
```

- 한 결정은 이 흐름 전체에서 **같은 문구·같은 값**으로 보인다. 화면의 "위임 · 정리드"가 초안과 기획 확인 화면에도 "위임: 정리드"로 나온다.
- 리드가 없는 회의(진행자가 팀장·랩 리드가 아님)는 지금처럼 할 일을 낱장 카드로 만든다. 초안은 만들지 않고, 결정 블록만 회의록에 붙인다.

## 3. 완료 기준 (스프린트 회의 결정 3가지)

| # | 기준 | 확인 방법 |
|---|---|---|
| 1 | **질문 원문 전체 저장**, 화면은 기본 2줄이고 펼치면 전문 | ① 줄 중간에 표시가 있는 발언, ② 질문 안에 `|`가 있는 발언, ③ 표시를 언급만 한 발언으로 회의를 돌린다. ①·② 질문이 잘리지 않고 `raw`가 남는다. ③ 결정 요청이 생기지 않고 발언이 남는다. 3줄 이상 질문은 답이 난 뒤 2줄로 접히고 "더 보기"로 전문이 보인다(미결정 카드를 펼칠지는 7절 Q3) |
| 2 | **결정 유형(직접/위임)과 결정자 기록**, 위임은 "위임" 라벨과 결정자 표시 | 선택지 답·직접 입력·"알아서 정해"·회의 끝내기를 PC·폰(v2)·비서 경로로 각각 해 본다. 저장값이 강백엔 문서 3-1 표와 같다. 화면 라벨이 이디자 문서 1절 매핑표와 같다. 옛 회의는 "위임 · 결정자 기록 없음"으로 보인다 |
| 3 | **요약(기획안 초안)과 화면 강조가 같은 결정 데이터를 읽음** | 결정 3건(직접 1·위임 1·끝내기 1)이 있는 회의를 끝내고, 회의 화면의 라벨·값과 결과 카드·기획 확인 화면의 결정 섹션을 비교한다. 문구·값·순서가 같다. 코드에서 결정 문구를 만드는 곳이 `decisionView`·`decisionLines` 한 곳뿐이다(리뷰에서 확인) |

함께 지킬 것: 두 번 전달 버그 수정 후 회의 결과 카드를 두 번 시작해도 리드에게 한 번만 가고, `task` 제목 없이 `propose_plan`이 통과한다.

## 4. 회의 종료 시 기획안 초안 자동 생성

### 4-1. 무엇을 만드나
진행자가 리드인 회의가 끝나면(`runMeeting`의 `meetingResultCard` 자리), 앱이 결과 카드 `detail`을 아래 **기획안 초안** 형식으로 만든다. LLM을 추가로 부르지 않는다. 결정은 `decisionLines`로, 할 일은 지금처럼 회의록의 `[할 일]` 줄로 만든다.

```markdown
회의 "{주제}" 결과로 만든 기획안 초안이에요. 순서와 세부 내용을 다듬어 mcp__office__propose_plan으로 올려 주세요.
결정 사항 두 섹션은 앱이 채우니 고치지 마세요(바꿀 결정이 있으면 기획서 "열린 질문"에 적기).

## 결론
{회의록 결론 한두 문장}

## 결정 사항(직접)
- {질문} → {선택} (대표)

## 위임 결정
- {질문} → {선택} (위임: {결정자}) — {이유}
- {질문} → (위임 · 결정자 기록 없음)

## 답하지 않음
- {질문} (회의를 끝내 답하지 않음)

## 할 일 (액션 아이템)
1. {제목} (담당 제안: {이름})
2. {제목} (담당 제안: 없음)

## 회의록
{회의록 전문}
```

- 결정이 0건인 섹션은 "없음" 한 줄로 둔다(섹션을 빼지 않는다. 리드와 대표가 "확인했는데 없음"과 "누락"을 구분할 수 있게).
- **위임 결정은 별도 섹션**이다. 대표가 기획 확인 때 "내가 직접 정하지 않은 것"을 한눈에 다시 볼 수 있게 한다.
- "답하지 않음"을 넣을지는 강백엔 문서 8-2의 제안(넣음)을 따른다(7절 Q2).

### 4-2. 카드와 회의 연결
- `Task`에 선택 필드 `meetingId?: string`를 더한다. 결과 카드를 만들 때 채운다. DB는 Task JSON에 들어가므로 마이그레이션은 **확인 필요**(박패턴·강백엔 확인 — Task 저장 방식이 회의와 같은 JSON 한 칸인지).
- `propose_plan`이 `meetingId`가 있는 카드의 기획안을 받으면 앱이 `spec`의 결정 세 섹션을 `decisionLines` 결과로 **덮어쓴다**(없으면 맨 위에 넣는다). 그래서 리드가 결정 문구를 바꿔도 기획 확인 화면에는 원본이 나온다 → 완료 기준 3.
- 할 일 항목은 지금처럼 `absorbs`로 묶는다(회의 할 일을 낱장으로 만들지 않는 지금 구조 그대로라 묶을 카드가 없으면 생략).

### 4-3. 제출과 승인
- 제출은 **리드의 `propose_plan` → 결재함 "기획 확인" → 대표 승인**으로 지금과 같다. 앱이 초안을 바로 결재함에 올리지는 않는다(하위 업무의 순서·세부 내용·담당 확정은 리드 몫이므로).
- 결과 카드는 지금처럼 리드에게 배정만 하고, 시작은 대표가 보드에서 누른다. 자동으로 시작할지는 7절 Q5.

## 5. 화면 흐름

| 단계 | 화면 | 사용자가 보는 것 | 바뀌는 점 |
|---|---|---|---|
| 1 | **회의 화면** (`MeetingPage`) | 발언 흐름 안의 결정 카드 | 미결정: 노랑·"답 대기"·선택지 버튼. 답한 뒤: 초록 "직접 결정" 또는 회색 바탕·주황 "위임 · {결정자}" 라벨. 질문은 2줄 + "더 보기/접기"(이디자 4절) |
| 2 | **결재함** (`InboxPage`) | 진행 중 회의의 대기 결정 | 같은 `DecisionBox`라 1과 똑같이 보인다. 뱃지 개수 규칙은 그대로(`answer === null`) |
| 3 | **단체방** | `🙋 결정 부탁드려요` → 위임 시 `🤝 위임 결정(정리드): 질문 → 선택` → `📋 회의록` | 위임 결정 한 줄이 새로 생긴다 |
| 4 | **업무 보드** (`BoardPage`) | "회의 결과: {주제}" 카드(할 일 칸, 담당 리드) | 카드 내용이 기획안 초안이 된다. 카드에 "기획안 초안" 표시를 둘지는 디자인 확인(7절 Q6). 시작 버튼 한 번에 한 번만 전달 |
| 5 | **결재함 — 기획 확인** | 리드가 올린 기획서·하위 업무 | 기획서에 "결정 사항(직접)"·"위임 결정"·"답하지 않음" 섹션이 앱 원본으로 들어 있다. [승인]·[다시 기획] 그대로 |
| 6 | **업무 보드** | 승인 뒤 하위 업무 카드가 결과 카드 아래로 | 지금과 같다(순서대로 진행 → 리드 취합 → 검토 칸) |

- 폰(v2)은 PC와 같은 화면 묶음을 쓰므로 1·2·4·5가 같이 바뀐다. 옛 APK는 새 필드를 무시하고 지금처럼 보인다(강백엔 5절).
- 업무 모드에서도 색이 같아 따로 할 것이 없다(이디자 2절).
